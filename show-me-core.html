@nyte-ai/core

Core saves the conversation and runs the agent.

Your app shows the chat. Core stores the messages, asks the model for a reply, and runs the tools the model requests.

It saves completed steps so another process can continue later. Several apps can send messages to the same conversation without overwriting each other's input.

01 · Sending

What happens when you send a message

Say you ask the agent to explain a file. The message takes this path.

  1. 1

    You send it

    The app submits your message to core.

  2. 2

    Core saves it

    Your message waits in a queue until the agent can use it.

  3. 3

    The agent works

    A runner asks the model, runs its tools, and saves the results.

  4. 4

    The app shows it

    The app receives updates as the reply comes in.

A runner is the code that does the next bit of agent work. A saved message can wait for a runner to become available. The host calls nyte.attach() to volunteer this process to run work. Sending alone does not start it.

See how a run moves forward

Inside the kernel, step reads saved progress and performs one action. drive repeats those steps under a lease. Apps use attach through the public SDK. Calling individual steps requires an integration with kernel internals.

Add a queued message to the conversation
  → ask the model for a reply
  → if it requests tools, run them and save their results
  → ask the model again
  → finish when there is nothing more to do

The saved run records whether to respond, run tools, wait for input, or retry at a given time. It also records when the run finishes, stops, or fails. A context summary is another saved conversation entry.

02 · Sharing a conversation

Many apps can send. One runner saves the next step.

Apps add messages to a queue. The runner takes them from that queue and adds them to the conversation. Sending a message does not require the runner's permission.

Messages do not overwrite each other

Before saving a queue update, core checks that the queue has not changed. If another app got there first, it reads the new queue and tries again.

An old runner cannot save over a new one

A runner needs temporary permission for its branch of the conversation. If another runner takes over, core rejects further writes from the old one.

See the send and run steps in code

App sends a message

read the queue's latest message
save the new message linked to it
update the queue if it has not changed

If it changed, read it and retry.
If the send key already exists,
return the original receipt.

Runner does a step

get permission for this branch
read the saved conversation and run
do the next action
save if permission and state still match

If another runner took over, stop.
If state changed, read it again.
  • The check before saving is called compare-and-swap, or CAS. Related changes all save together, or none do.
  • A lease is the runner's temporary permission. Its fence is a number that changes when another runner takes over.
  • Each queue is called a lane. The default steer lane adds messages before the next model response. The queue lane waits until the current run ends.
  • The default policy handles one message at a time and checks steer before queue. A host can choose other lanes, priorities, or drain all pending input at once.
  • Each lane tracks its newest submission and its last added message. Messages newer than the last added one are pending. Cancelling marks a message as withdrawn. It cannot both be cancelled and added.

03 · Recovering

After a crash, core checks what was saved.

A new runner reads the saved conversation and run. Queued messages are still there. For a tool call, the hard case is a crash after the tool acts but before core saves its result.

If the tool is safe to repeat

Its author can mark it safe. A new runner may run it again if no result was saved.

Reading a file is a common example.

If repeating it could cause trouble

The default is never. Core reports an interrupted call when it cannot tell whether the tool finished.

Sending an email twice could send a duplicate.

If a result is already saved, core reuses it. It does not run that tool call again.

See what core saves around a tool call
Saved stateWhat the next runner does
intentThe planned call is saved, but no result is known. Repeat it only if it is marked safe.
waitingKeep waiting for a reply or a request to stop. No process needs to stay running.
signalPass the first accepted reply to the tool's resume handler.
resultReuse the saved result.

A call can go straight from intent to result. Waiting is optional. If the host exits while a tool waits, a phone can reply an hour later. The next runner uses that reply to continue.

These records are called effects. They let core recover without promising that every outside action happens exactly once.

04 · Storage

Four things keep the conversation working.

The shipped backend is SqliteStore, exported from @nyte-ai/core/store. Within each session, it stores these four kinds of data.

Saved records objects
Messages, run progress, and tool results. Core writes new records instead of changing old ones.
Current positions refs
Labels that point to saved records, such as the latest message or current run. Core moves these labels when it saves progress.
Runner permission leases
Who may save the next step on a branch. Another runner can take over after this permission expires.
Updates for apps events
A numbered feed of changes, reply fragments, tool progress, and notices. Apps use it to keep the screen up to date.
See the storage names used in the code

An object ID, or oid, comes from hashing its contents. The same contents get the same ID. Core saves the object before pointing a ref at it. If the ref update fails, the unused object can be cleaned up later.

The six object kinds are commit, change, run, effect, stack, and blob. A commit is a saved conversation entry. A change is an entry waiting to be added.

Ref nameWhat it tracks
refs/heads/<head>The latest entry on a branch.
refs/stacks/<head>The parent branch and the point where a child branch started or last caught up.
refs/queues/<head>/<lane>/tipThe newest message submitted to this queue.
refs/queues/<head>/<lane>/baseThe last message added from this queue.
refs/runs/<head>The current run and what it should do next.
refs/effects/<run>/<call>The saved state of a tool call.

05 · Keeping the screen current

An app can disconnect and catch up later.

While the model writes, core sends reply fragments to the app. When the reply finishes, core saves it as a conversation entry.

  1. The app remembers the number of the last update it received.
  2. When it reconnects, it asks for updates after that number.
  3. If those updates are too old, it loads the current conversation and starts watching from there.
See how streaming and reconnecting work in code

A reply has no final object ID until its full contents are known. While it streams, fragments use the run ID, attempt number, and content index.

Reply fragment: "The "
Reply fragment: "answer is..."
Finished reply: save the full message and its object ID

The update number is seq. If the app's saved number is older than the retained events, the local SDK throws CursorExpired. The remote client reports cursor_expired in a NyteWireError. It calls sessions.snapshot, then watches after the snapshot's seq.

The product chooses how long to keep old events and unused objects. Undo works only while the required history is still saved.

06 · Long conversations

The model can read a checkpoint instead of the full history.

As a conversation fills the model's context window, core can save a checkpoint. With the portable summarizer, the next request contains a summary and recent messages.

See when compaction happens

Automatic compaction is enabled by default. Core checks whether context leaves fewer than 16,384 tokens free and can also compact after a context-overflow response. Portable compaction aims to keep about 20,000 recent tokens. The host can change these settings.

A plugin can supply provider-native compaction through before_compaction. When it succeeds, core saves that provider's compacted output. Otherwise it uses the portable summarizer. Native checkpoints also keep portable history for a model switch.

The local SDK exposes runs.compact for a manual checkpoint. It returns busy while a run is live or nothing_to_compact for empty context. The current HTTP protocol does not expose this method.

A branch keeps a different path through the conversation.

Each conversation entry has one context parent, or none at the start. A branch head points to its latest entry. Moving the head changes which path the model reads next.

With heads.move({ summary }), core can summarize the path you leave and add that summary after the target entry. If summarization fails, the head stays where it was.

Source: compaction, branch operations, and SDK.

07 · The rest of the app

The app supplies the screen, models, and tools.

The desktop app, terminal app, or server hosting core still has work to do.

  • Choose the model connection and load the plugins that provide tools and other behavior.
  • Build the chat screen from saved conversation data and incoming updates.
  • Keep an outgoing message locally until core confirms it was saved. Retry a failed send with the same key to avoid duplicates.
  • Attach a runner for the sessions this process should serve. The host also controls workspace trust before it loads workspace plugins.
See what the server and client provide

@nyte-ai/server is a request handler. It accepts SDK calls at POST /v1/call/{verb} and streams session events at GET /v1/watch. The host supplies authentication, starts the HTTP listener, and attaches a runner.

@nyte-ai/client calls those routes with fetch. Both packages use the schemas and verb table in @nyte-ai/protocol. The remote API currently exposes a subset of the local SDK, including send, cancel, snapshot, abort, and head moves.

The desktop and terminal hosts run core locally. A custom host that executes one kernel step per request still needs its own scheduling and storage integration.
