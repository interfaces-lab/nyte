Showing subagents in the terminal

Why five at once breaks the screen, and the three levels that fix it.

Start with what breaks

Here is uji today. One subagent, one line, and that line never moves for as long as it runs. 

● Used task, read, listed  1 task · 3 read · 1 ls
● task general
● read

the middle line is a subagent. it looks the same after two minutes.

That is annoying but survivable. Now launch five at once. This is what a shipped terminal agent actually renders: 

Running 5 agents…
Wait two minutes
Running in background
Wait two minutes
Running in background
Wait two minutes
Running in background
Wait two minutes
Running in background
Wait two minutes
Running in background

five subagents, same prompt. eleven rows of nothing.

Look at it for a second. Five pairs of identical rows. You cannot tell which one is which. You cannot tell which one finished. You cannot tell if any of them are stuck. And in a minute, when they are all done, these eleven rows will still say "Running in background", because they scrolled into the log and the log does not change.

And the picker is worse:

Subagents
  Wait exactly 2 minutes (120 seconds) before completing. You can use a sleep comm
  Wait exactly 2 minutes (120 seconds) before completing. You can use a sleep comm
  Wait exactly 2 minutes (120 seconds) before completing. You can use a sleep comm
  Wait exactly 2 minutes (120 seconds) before completing. You can use a sleep comm
  Wait exactly 2 minutes (120 seconds) before completing. You can use a sleep comm

a list whose whole job is letting you pick one, with five rows you cannot tell apart, cut mid-word.

Three things went wrong

1. Nobody gave them names

The label on each row is a short description the model was asked to write. Five subagents got the same task, so the model wrote the same description five times. Of course it did.

Here is the tell. The prompt that launched these ends with: "reply with a single sentence confirming you waited 2 minutes and which agent number you are: Agent 1." The person running this numbered the agents by hand, inside the prompt, because the interface would not do it.

So: never ask the model for identity. Ask it for a description, sure, that is useful. But the number is ours to assign. Task 1 through 5, fixed for the life of the run. One character wide, never collides, and you can say it out loud. "Kill 3."

2. Live state was written into history

This one we already learned and wrote down. From pending-gutter.ts, about queued messages:

The transcript is an append-only record, so drawing them inside it made a mutable list look like history: consuming one deleted a block from the middle and shifted everything below it, and scrolling up hid the one thing worth taking back. They live in their own region instead, a sibling of the scroll box, pinned above the composer.

Running tasks are the same kind of thing. They change, they finish, they fail. A transcript row cannot represent that, because the moment you scroll the row is gone and the moment it settles the row is a fossil. The screenshot above is a list of five things that stopped being true.

3. It cost eleven rows to say nothing

On a normal terminal that is half the screen. The information content is "five things are running", which is six words. Two rows per task, one of them spent on the word "background", is the wrong trade at any count above one.

The thing I got wrong earlier

I sketched nesting: the child's transcript indented under the parent's row, behind a bar. For one subagent it is fine. For five it is the same disaster with better punctuation.

Nesting works on a web page because a page can collapse a region and reflow around it. A terminal transcript cannot. Once a block scrolls past, folding it does nothing you can see, and unfolding it shoves everything below it down. Depth in a terminal is not something you draw. It is somewhere you go.

So the answer is navigation, not indentation. Three levels, and each one is a place, not a layer.

Level one: a row that does not lie

Two rows, actually, and they have different jobs.

In the transcript, the parent says what it did, past tense, once, and then never changes. That is what a log is for. 

✓ Delegated 5 tasks  general ×5 · 4 done · 1 failed · 2:11

history. true when written, still true tomorrow.

The live part sits above the composer, in the same region the pending queue already uses. It is one line, it counts, and it never scrolls away. 

✓ read  packages/tui/src/transcript.ts · 1854 lines                   
✓ Delegated 5 tasks  general ×5                                       

─────────────────────────────────────────────────────────────────────
⠙ 5 tasks  3 running · 1 done · 1 failed · 1:04                ↓ tasks
❯ Add a follow-up

pinned. five tasks in one row, and the key that opens them.

This row is not interactive. You cannot focus it, click it, or tab into it. It is a readout with one hint on the end. Everything you might want to do happens after you press the key, which keeps the composer's behaviour unchanged while you are typing.

Level two: press down

Down already does two things in the composer. It walks the rows of a multi-line draft, and at the bottom of the draft it hands over to message history, the way a shell does. We add a third step at the end of that chain: empty draft, tasks running, down opens the task list. 

Tasks  5 · background shell and subagents                      esc close

❯ 1 general  Wait two minutes   running  1:04  sleep 95                 
  2 general  Wait two minutes   running  1:02  sleep 120                
  3 general  Wait two minutes   done     2:00  waited two minutes       
  4 bash     pnpm build         running  0:48  compiling tui            
  5 general  Wait two minutes   failed   0:03  context exceeded         

enter open · x cancel · X cancel all

the settings menu, with a fourth column that does the real work.

The last column is the point. Two subagents with the same prompt and the same description are still doing different things right now. One is on sleep 95, the other on sleep 120. That is what tells them apart, and it is the only column here that could not have been written in advance.

Note the fourth row. That is a shell command, not a subagent, sitting in the same list. From where you are standing they are the same object: something you started, that is still going, that you might want to look at or stop. One list, one shape, one set of keys.

Level three: the whole screen, read only

Enter on a row takes over the terminal. Not a panel, not a split, the whole thing.

╭─ Task 1 of 5 · general · running · 1:04 ───────────────────────────╮
│                                                                    │
│ Wait exactly 2 minutes (120 seconds) before completing.            │
│                                                                    │
│ Waiting 120 seconds, then I'll confirm.                            │
│                                                                    │
│ ✓ bash  sleep 120  backgrounded at 30s                             │
│ ● bash  sleep 95                                                   │
│                                                                    │
│ ⠙ Working                                                          │
│                                                                    │
╰─ ↑↓ scroll · ←→ task · x cancel · esc back ────────────────────────╯

left and right move between tasks without going back to the list.

You cannot type into this. That is deliberate, and it is the reason this shape is cheap while a docked panel is expensive.

A panel that shares the screen with the composer has to answer "where do my keystrokes go" on every single frame, and it has to answer it while you are mid-word. Escape has to mean two things. Every new key has to be checked against the composer's bindings. A full screen with no text input never asks the question. Up and down scroll. Escape goes back. There is nothing else it could mean.

One detail worth stealing from that screenshot: the child ran sleep 120, the harness backgrounded it at thirty seconds, and the child then ran sleep 95 to make up the difference. A background job inside a background job. If we let shells background themselves we need a rule for that, and the honest one is that a task shows its own children as ordinary rows and never opens a fourth level.

What this needs from core

Most of it, nothing. The child's id arrives on the first progress update, we can watch any session by id, and cancelling one is an abort against the child's own run. The number, the columns, the keys and the screens are all ours.

Two things are missing, and they are really one thing.

What the design needs Have it?
Child id while it runs yes
Watch a child's transcript yes
Cancel one child yes
Several running at once yes
A shell that keeps running in the background no
One list holding both kinds no

Row four of that task list does not exist yet. There is no background shell, so there is nothing to put next to the subagents, so there is no reason for the list to be called "tasks" instead of "subagents".

opencode solved this by not having a subagent feature at all. They have a registry of background work with two kinds of entry in it, shell and subagent, and the subagent tool is a short function that adds one. Start it, block on it, or walk away from it. Both kinds recover the same way when the server dies.

That is the shape to copy, and our own design doc already describes it in passing. It is one change, not two, and it is what turns this list from a subagent inspector into the place where anything still running lives.

What survives from the five sketches

  • The moving line survives, but pinned above the composer rather than in the log.
  • The list survives and gets promoted. It is level two.
  • Nesting is out. It reads fine at one child and falls apart at five.
  • The docked panel is out for good, replaced by the full screen, which costs less and asks nothing of the composer.
  • The summary card is out. Its one good line, the counts, is already on the settled transcript row.

What is left is smaller than what I started with and it holds at five. That is the whole test.
