---
title: Print mode
description: Send one prompt with nyte -p, stream the answer to stdout, and script around its JSON output and exit codes.
---

Print mode sends one prompt, streams the answer, and exits. Use it in scripts, git hooks, CI jobs,
or anywhere you'd pipe a command.

```sh
nyte -p "Summarize what changed in the last commit"
```

The agent works in the current folder, the same as in the [interactive client](/docs/cli). Each
run is a saved chat, so you can open it afterwards or send it another prompt.

## When print mode starts [#when]

Any of these selects print mode:

- `-p` (`--print`), `--json` or `-q` (`--quiet`)
- stdin isn't a terminal, for example `git diff | nyte`
- stdout isn't a terminal and you gave a prompt, for example `nyte "explain this repo" > notes.md`

## The prompt [#prompt]

The words after the flags are the prompt, joined with spaces. Without them, `nyte` reads the prompt
from stdin and drops one trailing newline:

```sh
git diff --staged | nyte -p
nyte -p < prompt.md
```

If you give both a prompt argument and nonempty piped or file input, `nyte` rejects the command.
To send instructions and piped input together, put both on stdin. An empty prompt exits with 2
and the reason `missing_input`.

## Continue a chat [#continue]

| Command                                   | Where the prompt goes                                   |
| ----------------------------------------- | ------------------------------------------------------- |
| `nyte -p "prompt"`                        | A new chat in the current folder                        |
| `nyte -p --resume "prompt"`               | The chat with the most recent activity, from any folder |
| `nyte -p --session <session-id> "prompt"` | That chat                                               |

In print mode `--resume` takes no session id: the text after it is the prompt. Use `--session` to
name a chat.

The [flags](/docs/cli#flags) `--model`, `--provider`, `--effort`, `--trust`, `--no-trust`,
`--no-context-files` and `--host-url` work here too. `--model` also becomes your default model for
later chats.

## Output [#output]

The answer streams to stdout. stderr gets the name of each tool the agent calls, then a receipt
with **Completed**, the session id and the command that opens the chat. On failure, stderr gets
the error, any available details and suggested recovery commands instead.

`--quiet` drops the tool names. Startup progress, such as starting a host, can still appear on
stderr.

To open the chat later and see everything the agent did, run the printed command in a terminal.

## JSON output [#json]

`--json` writes one JSON object per line to stdout, and nothing else:

```jsonl
{"type":"text","text":"The last commit "}
{"type":"tool","name":"read"}
{"type":"text","text":"renames the config loader."}
{"type":"result","outcome":"completed","session":"<session-id>","next":[{"command":"nyte -p '--session=<session-id>' '<PROMPT>'","argv":["nyte","-p","--session=<session-id>","<PROMPT>"],"when":"Send a follow-up in place of <PROMPT>"},{"command":"nyte '--session=<session-id>'","argv":["nyte","--session=<session-id>"],"when":"Open the chat in a terminal"}]}
```

| `type`   | Fields                                                       |
| -------- | ------------------------------------------------------------ |
| `text`   | `text`: the next piece of the answer                         |
| `tool`   | `name`: a tool the agent called. Absent with `--quiet`       |
| `result` | The final stdout record, emitted only when the run completes |

Concatenate every `text` to get the full answer. A successful `result` has these fields:

| Field     | What it holds                                                                        |
| --------- | ------------------------------------------------------------------------------------ |
| `outcome` | `completed`                                                                          |
| `session` | The chat's id                                                                        |
| `next`    | Suggested commands as an array, each with `command`, `argv` and a `when` description |

A run that fails, is stopped or needs input does not emit a `result`. Failure reports are JSON
objects on the final line of stderr, after any startup progress:

| Field     | What it holds                                                                                     |
| --------- | ------------------------------------------------------------------------------------------------- |
| `status`  | `action_required` when input or a human step is needed; otherwise `error`                         |
| `reason`  | An [error reason](#result-codes), such as `input_required` or `run_failed`                        |
| `message` | What happened                                                                                     |
| `next`    | Suggested recovery commands in the same array shape as a result's `next`. Absent when none apply  |
| `data`    | Details specific to the error, such as `session`, `questions` or `remote`. Absent when none apply |

Check the exit code as well as the records: a cleanup failure can follow a completed `result`,
and forced termination can prevent the final report from being written.

## Exit codes [#exit-codes]

| Code  | Meaning                                                                                                |
| ----- | ------------------------------------------------------------------------------------------------------ |
| `0`   | The run completed                                                                                      |
| `1`   | The run failed, another client stopped it, its outcome is unknown, or another non-usage error occurred |
| `2`   | Invalid arguments or missing input, including when the agent asks a question                           |
| `130` | Cancellation, including Ctrl+C (`SIGINT`)                                                              |
| `143` | `SIGTERM`                                                                                              |
| `129` | `SIGHUP`                                                                                               |

When the agent asks a question, `nyte` stops the run. Use the suggested follow-up command to
answer, or open the saved chat in a terminal.

A signal asks the host to stop the run. Nyte waits briefly for confirmation, but can exit while
the host is still stopping it. The cancellation report's `data.remote` can be `stopping` or
`unknown`; open the saved chat to check before retrying actions in those states.

## Error reasons [#result-codes]

Common reasons in a JSON error report:

| `reason`                                                 | When                                                                                                 |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `missing_input`                                          | A prompt or another required input, such as a usable model credential, is missing                    |
| `input_required`                                         | The agent asked a question. `data.questions` holds the questions and choices                         |
| `run_stopped`                                            | Another client stopped the run                                                                       |
| `canceled`                                               | The command was canceled. `data.remote`, when present, reports what Nyte knows about the run's state |
| `run_failed`                                             | The run failed. `data.failure` gives the class and `data.remoteMessage` gives the underlying message |
| `unknown_outcome`                                        | Nyte lost track of the run, which may still be running. Open the chat before retrying                |
| `unknown_command`, `unknown_option`, `invalid_arguments` | The command or its arguments are invalid                                                             |
| `not_found`                                              | A named model, session or other resource could not be found                                          |
| `network_error`                                          | Nyte could not reach the host                                                                        |
| `failed`, `internal_error`                               | Another failure occurred, including startup or cleanup failure. Read `message` and any `next` steps  |

## Examples [#examples]

Review staged changes before committing:

```sh
{ echo "Review this diff. List bugs only."; git diff --staged; } | nyte -p -q > review.md
```

Check the outcome in a script, using `jq` to read any suggested recovery commands. Capture stderr
separately because run errors are reported there, not in a stdout `result`:

```sh
status=0
nyte -p --json "Run the tests and fix any failure" > run.jsonl 2> run.stderr || status=$?
if [ "$status" -eq 2 ]; then
  echo "Input is needed. Suggested commands:"
  tail -n 1 run.stderr | jq -r '.next[]?.command'
elif [ "$status" -ne 0 ]; then
  cat run.stderr >&2
fi
exit "$status"
```

Ask a follow-up in the same chat:

```sh
nyte -p "Find why the date test is flaky"
nyte -p --resume "Now add a regression test"
```
