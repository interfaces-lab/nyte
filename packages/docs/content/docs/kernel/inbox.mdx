Submitting never touches the head. The submitter stamps `kind` and `delivery` on the change, and nothing infers them later. An automatic delivery is `steer` while the head has a live run and `next` otherwise.

On one `Nyte`, `messages.send`, `sessions.configure` and `plugins.settings.apply` for a session are admitted in call order. A setting applied just before a send is stored before that send is admitted. Nothing pins a setting to a message: a request reads settings when it is built, so an apply after the send still changes what its run sees. A command's writes are done when `plugins.commands.run` returns; it runs outside this order because a command may call the model.

## Two chains

Each head has a `steer` chain and a `next` chain, each with a `tip` and a `base`. A change names the tip it followed in `previous`, so pending is `(base, tip]` read back from the tip and no ref holds a list. `steer` lands at every response boundary and when the head is idle. `next` lands only when the head is idle and `steer` waits. `pending` merges the two chains by submission time without reordering either, so a redelivered copy, which keeps its time, stays where `before` put it.

`drain` sets how much one landing takes. `"one"` takes everything through the first `user` change, so a `report` or `passive` change queued ahead of it lands with it, and a chain with no `user` change lands whole. `"all"` takes the chain.

## Cancel and redeliver

Only a landing or a cancel takes a change out of pending, so a run that fails, aborts or is superseded leaves every pending change where it was. A cancel that races a landing has one winner. If the landing wins, the cancel reads again and answers `landed`.

`redeliver` changes a pending item's `delivery`, moves it with `before`, or replaces a pending user message's content, in one CAS. It tombstones the change and every change after the splice point, asserts the source base, and rewrites that suffix after the target's tip.
