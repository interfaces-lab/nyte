This page defines `@nyte-ai/core` contracts and overrides conflicting documents. The tree and tests
determine shipped behavior.

## What core is

Nyte core is a durable runtime for agent conversations.

- **It runs anywhere.** The same kernel runs in an Electron main process, under a TUI, on a VM,
  and in request-scoped infrastructure. Each step reads all durable state. A long-lived process
  is an optimization, never a requirement.
- **Any number of participants may write at once.** Phones, web pages, desktop apps, and cloud
  jobs may submit to one session. Participant writes never take the runner's lease. They
  linearize through compare-and-swap and retry expected conflicts.
- **Accepted input is not lost and published history is not rewritten.** Objects are immutable,
  and refs identify current objects. A failed publish leaves a loose object, not a partial
  transaction.

A kernel change must preserve these four acceptance scenes.

1. Three phones submit at the same moment to `next` on an idle head. Every submission
   succeeds. The tip retries form one change chain and the oldest change starts a run. The rest
   stay pending until that run ends and the head is idle again. Nobody gets a contention error and
   nothing is lost.
2. A run is killed after a tool intent but before a result. Another process acquires the expired
   lease. It runs a `safe` effect again, or settles a `never` effect as interrupted, then carries on
   from refs. The client watching sees a pause and nothing else.
3. A tool parks in `waiting`. The asking host exits. An hour later a phone signals the effect. The
   first signal compare-and-swap wins, and whichever runner next acquires the head wakes and
   settles the call.
4. A serverless handler submits a change, runs one durable step, streams events, and exits. The
   next request or alarm reads the run ref and takes the next step. No process-local run state is
   needed.

### Facts we accept

| Fact                                                   | Mechanism                                                                       | Section                                 |
| ------------------------------------------------------ | ------------------------------------------------------------------------------- | --------------------------------------- |
| The process can die at any moment, or never existed    | Every uncertain tool call moves an effect ref from intent to result             | [Runs](#runs)                           |
| Any process may be the one that continues a run        | A runner keeps nothing in memory across a step                                  | [Many runners](#many-runners-one-store) |
| Writers race constantly                                | Multi-ref CAS, internal submission retry, and fenced runner publishes           | [Admission](#admission-is-open)         |
| Providers cache the context prefix                     | `steer` lands at response boundaries; `next` waits for an idle head             | [Admission](#admission-is-open)         |
| The outside world will not join a database transaction | Per-effect replay policy instead of impossible exactly-once execution           | [Runs](#runs)                           |

### Roles

One process can play several roles. The TUI plays all six. A phone plays only client.

| Role   | Is                                                                                                               |
| ------ | ---------------------------------------------------------------------------------------------------------------- |
| store  | The four durable authorities: objects, refs, leases, and events. A session is one repository.                    |
| runner | Code that holds a fenced lease over one head and advances its run one durable step at a time.                    |
| host   | A process that opens the store, supplies models and plugins, and may volunteer runners.                          |
| client | Code that calls SDK operations, renders snapshots and events, and keeps a cursor plus a local submission outbox. |
| plugin | Host-side code that contributes model context, tools, commands, settings, resources, and policy.                 |
| schema | The shared message and JSON types used at the object boundary, by the agent loop, and by clients.                |

Protocol defines client-rendered `Choice`, `Selection`, setting, notification, and status data.
They are never calls.

## The model, in git terms

| git                           | core                                                                             |
| ----------------------------- | -------------------------------------------------------------------------------- |
| object database               | `objects`: immutable values addressed by the SHA-256 hash of their body          |
| commit with parent            | conversation commit with exactly one context parent                              |
| extra parent or provenance    | `imports`: provenance that never joins model context                             |
| branch ref                    | `refs/heads/<head>`                                                              |
| HEAD                          | the head name supplied by the client, never a stored checkout register           |
| detached read                 | reading at any commit without moving or checking out a head                      |
| `update-ref` compare-and-swap | one atomic `refs.update` over any number of refs                                 |
| lock file                     | a fenced lease over `refs/heads/<head>`                                          |
| reflog                        | retained `ref` events in the session event stream                                |
| index                         | two pending inbox chains per head, behind delivery tip and base refs             |
| stack metadata                | `refs/stacks/<head>` pointing to `{ parent, base }`                              |
| rebase                        | never replay generated text; the model writes a summary commit for carry-forward |
| worktree                      | none; a client reads any commit and a runner reads refs at every step            |
| garbage collection            | mark from refs and retained ref events, wait through a grace period, then sweep  |

A commit has one `parent`, or `null` at a root. Only that chain becomes model context. `imports`
record summarized or carried commits as provenance and **must not** add another context path.

## The four authorities

### Objects

An object's body is RFC 8785 JSON with sorted keys and no whitespace. `hashObject` returns its
SHA-256 hex. The store checks the body against the oid on every read. Putting the same value again
returns the same oid without rewriting it. Most objects carry a write time, so retries usually
create a new object. `refs/keys/<key>` makes retries safe.

| Object   | Meaning                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------- |
| `commit` | One point in a conversation, with one parent, a body-specific provenance variant, and shared identity fields. |
| `change` | A commit body waiting for a parent, stamped with its kind and delivery and linked within that delivery.       |
| `run`    | One head's current run, including its phase, attempts, folded configuration, and optional abort request.      |
| `effect` | One tool call's durable state: `intent`, `waiting`, `expired`, `signal`, or `result`.                         |
| `stack`  | The parent head and base commit for a stacked head.                                                           |
| `blob`   | A small JSON value behind a fact, job record, compaction record, cancellation marker, or deletion marker.     |

Every commit can name its submitted `change`, submission `key`, writing `run`, and `author`. A
user message or background `completion` has `start`, which records either that no run started there
or the new run's initial workspace tree. An assistant message has a complete `calls` map and an
`outcome` of `ok` or a classified `Failure`. A tool result has its settled `call` class and the
workspace `tree` after the batch. Only a `summary` has `imports`, naming summarized commits. These
fields are provenance and never reach the model.

| Commit body  | Meaning                                                                                                          |
| ------------ | ---------------------------------------------------------------------------------------------------------------- |
| `message`    | One schema `Message`: user, assistant, or tool result, with the agent its submission selected.                   |
| `completion` | A finished background job's output, consumed by the model without impersonating user input.                      |
| `checkpoint` | A context checkpoint with a summary, retained tail, token count, optional provider material, and optional usage. |
| `summary`    | What a path being carried forward was about. It does not cut context.                                            |
| `config`     | A model, thinking level, or agent declaration. The latest value of each field wins.                              |

Objects **must** be written before a ref makes them reachable. A failed update may leave loose
objects, which retention collects after the grace period.

A streaming assistant message has no commit oid until complete. Provisional deltas name
`(runId, attempt, index)`; settlement supplies the finished commit's oid.

### Refs

Refs are the only mutable domain state. One multi-ref compare-and-swap moves them. Each update
names the expected oid in `from` and the desired oid or absence in `to`. The store checks every
expectation before atomically writing refs and ref events.

`to === from` is an assertion. The store checks it without writing a row or emitting an event.
Cancellation and redelivery use assertions to close landing races. A runner publish moves head or
run refs, carries its lease, and asserts `refs/deleted` absent.

```text
refs/heads/<head>              branch tip; absence means unborn
refs/stacks/<head>             Stack { parent, base }
refs/inbox/<head>/steer/tip  newest Change for the next boundary
refs/inbox/<head>/steer/base last landed steer Change; pending is (base, tip]
refs/inbox/<head>/next/tip   newest Change for the next idle head
refs/inbox/<head>/next/base  last landed next Change; pending is (base, tip]
refs/runs/<head>               current Run object and phase
refs/chains/<root>             Blob { attempts } shared by every run in one delegated chain
refs/compactions/<head>        checkpoint work in flight under the head lease
refs/effects/<run>/<call>      Effect: intent -> waiting -> signal/expired -> result
refs/jobs/<job>                Blob recording one background job
refs/delegations/<child>/<change> Blob recording one child request, continuation authorization, and delivery
refs/keys/<key>                idempotency receipt naming the Change
refs/facts/<key>               Blob holding a small session value
refs/cancelled/<change>        Blob tombstone for a withdrawn Change
refs/deleted                   Blob marking a session being deleted
```

Head names are open. Each head has only `steer` and `next` inbox delivery. The SDK defaults to
`main` and lists it before its ref exists.

### Leases

A lease grants fenced execution authority over one name. Runners acquire the head ref name. A
lease has `name`, `owner`, `fence`, and `expiresAt`. Leases record liveness, never history, so they
do not enter the object graph or reflog.

Acquire creates a lease when none exists. After expiry, takeover changes the owner and increments the
fence. Losing an acquire returns the current holder, not an exception. Renew and release match
both owner and fence. Renew ignores expiry for a matching holder. Expiry permits takeover but is
not an execution budget.

Every runner ref update and event append **must** carry the lease. The transaction checks the
stored owner and fence. A mismatch returns `fenced` before changing any ref or event.

### Events

Events form the reflog and live feed. An increasing `seq`, starting at 1, orders every event in a
session:

| Event      | Meaning                                                                    |
| ---------- | -------------------------------------------------------------------------- |
| `ref`      | One written ref move with name, from, to, reason, and optional actor.      |
| `delta`    | One text or thinking fragment keyed by run id, attempt, and content index. |
| `progress` | One tool call's partial output keyed by run id and call id.                |
| `notice`   | An informational, warning, or error notice owned by a component.           |

In one transaction, `refs.update` appends one `ref` event per ref write, then any extra events.
`events.append` adds deltas, progress, or notices without moving a ref and may be fenced by a lease.

`read` and `watch` yield events after a cursor in sequence order. `last` returns the newest
sequence. `floor` returns the oldest valid cursor boundary. Trimming removes events at or below a
chosen sequence and raises the floor, never past the newest event. Reading below the floor throws
`CursorExpired`.

## Heads are named refs

Clients may use different heads in one session.

### Moves and live runs

A participant moves a head by compare-and-swap from the oid it read. Optional `expect` rejects an
already stale view. A non-null target **must** name an existing commit. Kernel outcomes are
`moved`, `moved_since`, and `not_found`.

SDK `heads.move` applies `navigationTarget` first. Selecting a user message restores it to the
composer and targets its parent. With `summary`, one commit summarizes the abandoned commits and
uses that target as its parent. One CAS moves the head from the expected old tip to the summary.
If nothing was abandoned or the summary is empty, it falls back to a plain move. Generated text is
never replayed. A summarization failure returns `failed` without moving the head.

A kernel move neither takes the runner's lease nor waits for a live run. The SDK returns `busy` for
a live run. If a run races that check, its publish fails. The runner re-reads and moves the same run
to `aborted` with event reason `superseded`, without moving the participant's head or consuming
queued input.

Undo is another move. The kernel **must not** promise undo beyond the configured event and object
retention window.

### Branching

Creating a head from another head copies its tip and writes a stack object naming that parent and
tip as the base. Cutting from an unborn parent records no base. Creating from a commit writes only
the head ref. An unborn head therefore needs a stack parent, and moving it to a commit creates it.
The SDK cuts from and moves only listed heads or the default head. A mistyped name creates nothing
and returns `unknown_parent` or `not_found`.

One CAS deletes a head ref, stack, both deliveries' tip and base refs, and run ref. A live lease
returns `busy`. The kernel deletes any head, but the SDK refuses its default head.

### Stacks

`refs/stacks/<head>` points to `Stack { parent, base }`. A stacked head is stale exactly when
`base !== parent.tip`.

- `advanceBase` returns `unchanged` when there is no stack or the base already matches. If the old
  base is still an ancestor of the parent's tip, it updates only the stack base and returns
  `advanced`. If the parent diverged, it returns `diverged`.
- `fastForward`, exposed by the SDK as `heads.merge`, requires a current stack and a non-empty
  child. One CAS moves the parent head to the child tip and advances the child's stack base to the
  same oid. Its outcomes are `merged`, `stale`, `empty`, and `no_stack`.

## The turn

The kernel turn has two calls separated by one commit boundary:

```ts
interface Turn {
  respond(input: TurnInput): Promise<RespondOutcome>;
  tools(input: TurnInput & { assistant: AssistantMessage }): Promise<ToolBatchOutcome>;
}
```

`respond` receives the session, lease, run, attempt number, commits since the newest checkpoint,
an event emitter, and an abort signal. It projects model context and streams one assistant
message. Its outcomes are `checkpoint`, `complete`, `tools`, `retry`, `failed`, and `aborted`.
Except for `checkpoint`, each carries the complete assistant message to commit. `checkpoint`
carries a checkpoint body, which the step commits before calling `respond` again. Compaction is a
commit, never a special phase.

`tools` receives the same durable inputs and the committed assistant message. It recovers or
executes each call through its effect ref. Outcomes are `complete`, `waiting`, `failed`, `fenced`,
and `conflict`. Complete and failed outcomes carry tool-result messages in call order. Waiting
names parked call ids. `fenced` and `conflict` end the batch without committing after a lost lease
or raced effect CAS.

The turn emits text and thinking deltas with the supplied attempt number. A fenced outbox buffers
and flushes emissions before the call returns. A fenced event append aborts in-flight work.

### The tool batch

A `length` stop returns an error result for every tool call because truncated arguments cannot be
trusted. Tool failures settle a structured error result with the last partial progress available.
Results follow the assistant message's call order.

No turn state survives the call. A resumed `tools` phase re-reads the assistant commit and every
effect ref.

## Runs

`refs/runs/<head>` points to the current immutable `Run`. Each phase change writes a new object
and moves the ref while the run id stays stable.

A run records `id`, `head`, `origin`, `root`, `phase`, `startedAt`, `attempts`, and its folded branch
configuration. A user run has `origin: { kind: "user" }` and is its own root. A delegate continuation's
origin names the child session and request, and it inherits the requesting run's root. Before
publishing, the SDK runner resolves model and thinking defaults into the configuration. Before
responding, it resolves legacy runs and records any fallback needed when a successor host cannot
supply the recorded model. Observers use the run's inputs, not their host defaults. An idle
snapshot combines declared configuration with the last recorded or observed response inputs, which
in legacy history may lack a thinking level. A participant may set `abortRequested`.

| Phase     | Meaning                                                                           |
| --------- | --------------------------------------------------------------------------------- |
| `respond` | The next step may land a `steer` change, then ask the model for an answer.        |
| `tools`   | The assistant message has tool calls to recover or execute.                       |
| `waiting` | At least one effect is parked until a signal, deadline, or abort arrives.         |
| `retry`   | A provider attempt failed transiently and may resume at the stored time.          |
| `done`    | The run completed.                                                                |
| `aborted` | The participant, host signal, deletion, or superseding head move stopped the run. |
| `failed`  | The run ended with the stored error.                                              |

### Leases and the step

`step(session, turn, options)` acquires a head lease unless supplied one, performs one durable
action, and releases a lease it acquired. `drive` acquires once, renews before each step, loops over
`continue`, waits through retry deadlines, and releases on return.

The step first settles leftover checkpoint work in `refs/compactions/<head>`, then reads the head,
run, and deletion refs. A
session being deleted makes every step `idle`. Otherwise:

| Head / phase       | Lead                                 | Decision and step                                                                           | Publish CAS                                            |
| ------------------ | ------------------------------------ | ------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| idle               | none, report, or unauthorized answer | `wait`: return `idle`; keep the batch pending                                               | none                                                   |
| idle               | user                                 | `start`: land the batch and start a new user run and chain                                  | head, inbox base, run, chain                           |
| idle               | authorized answer                    | `start`: land the batch, inherit its root, consume authorization, and start a continuation  | head, inbox base, run, authorization                   |
| idle               | passive                              | `settle` under the terminal run; without a terminal run, `wait`                             | head, inbox base, run assertion                        |
| live `respond`     | none                                 | `wait`, then call `turn.respond`                                                            | assistant commit, run phase                            |
| live `respond`     | user, passive, report, or answer     | `join` the batch; if its agent changed, `handoff` ends the run and keeps the batch pending  | head and inbox base for `join`; run only for `handoff` |
| settling `respond` | any                                  | `wait`, then end the run `aborted`; keep every batch pending                                | run                                                    |
| `tools`            | any                                  | call `turn.tools`, commit settled results, or park                                          | result commits, effects, run phase                     |
| `waiting`          | any                                  | wake on a signal, expiry, completed results, deadline, or abort; otherwise return `waiting` | as `tools` when it wakes                               |
| `retry`            | any                                  | return `retry` before `at`; afterwards act as `respond`                                     | none until responding                                  |

Three rules apply within `respond`:

1. An existing abort request stores `aborted` without calling the model.
2. If projected context ends with neither a user message nor a tool result, the run goes to `done`.
3. If a pending batch selects another agent, the step ends the run as `done` for `agent changed`,
   lands nothing, and leaves the batch queued for the next run.

A participant head move, run-ref change, abort request, or session deletion may fail a runner
publish. The runner then re-reads, acts on current refs, and **must not** force stale output.

Before `turn.respond`, the step checks the chain's attempt ceiling. `refs/chains/<root>` points to
`Blob { attempts }`. Each provider call reserves an attempt by moving that ref in its own CAS. A
reservation conflict ends the losing run at the ceiling instead of retrying. A user message starts
a new root and counter. Reaching the ceiling stores a runner failure.

### The effect sandwich

Each tool call owns `refs/effects/<run>/<call>`. The ref moves through immutable effect objects:

```text
                   +-> signal --+
intent -> waiting -|            +-> result
   |               +-> expired -+
   +------------------------------>
```

The runner writes `intent` before executing the tool. The intent stores the run id, call id, tool,
JSON arguments, replay policy, and time. Recovery depends only on the ref state:

| State     | Recovery                                                          |
| --------- | ----------------------------------------------------------------- |
| `intent`  | execute again for `safe`; settle an interrupted error for `never` |
| `waiting` | remain blocked unless the run is aborted or its deadline passes   |
| `expired` | call the tool's wake handler with `expired: true`                 |
| `signal`  | call the tool's wake handler with the first reply                 |
| `result`  | reuse the stored tool-result message and never execute again      |

A missing replay policy defaults to `never` because the kernel cannot know whether a tool is
idempotent.

A tool parks by moving its effect to `waiting`. A participant CAS moves that exact waiting oid to
`signal`; at the deadline, a runner CAS moves it to `expired`. Only one wins. The runner then calls
the wake handler. A later reply returns `not_waiting`. The handler may settle or park again.

One runner CAS completes a tool batch by advancing the head with result commits, returning the run
to `respond`, and deleting the run's effect refs. A failed batch stores a failed run. A waiting
batch stores phase `waiting` and keeps effect refs.

Exactly-once execution is not promised. `safe` is at-least-once after an uncertain crash. `never`
is at-most-once and reports an unknown outcome after interruption.

### Wait and wake

A waiting run needs no process or held lease. Its run and effect refs hold its resume state. A ref
event or deadline wakes a runner but does not authorize a new run. Only user input or an
[authorized answer](#a-submitted-message-is-never-lost) starts one.

`runs.reply` targets a call id and its exact `waitId`, optionally checks a run id, and uses the
effect signal CAS.

A `waiting` step calls tools again when any effect has a signal or expiry, every effect has a
result, the nearest deadline passed, or the run has an abort request. Otherwise it returns `waiting`
with the nearest deadline for host scheduling. Submitted messages remain in the inbox. A tool reply
is a signal, never a conversation message.

A waiting effect may carry a `selection`. A `Selection` has a title, a non-empty list of `Choice`
items with ids and labels, optional `multiple: true`, and optional `other` as the placeholder for
the participant's own words. `SelectionReply` keeps selected ids separate from own text, so text
that looks like an id stays text. The selection is data on the ref, `effect` event, and snapshot's
`parked` list. Its `waitId` identifies the exact waiting effect. Snapshot order follows the
assistant message's tool-call order, with no other stored order. Re-parking creates a new `waitId`,
so clients discard local picks and reopen the wait. A wait without a selection is background work,
and a client **must not** present it as input. Core and clients use selection presence, never the
tool name. Core checks the `Selection` schema before writing it; a malformed selection fails the
call as a tool error.

A waiting effect may carry `until`, a durable epoch-ms deadline. At or after it, a participant
reply returns `not_waiting`, and the wake handler receives `expired: true` and no reply. A crash
after the expiry CAS leaves the next runner an `expired` effect. The handler settles or parks again
with a new `waitId` and deadline. Closing a Desktop or TUI panel never settles the effect; a host
step does. Local timers only hint wake-up and must recheck the epoch deadline, including deadlines
beyond the platform's maximum timer delay.

`await`, `task`, and `send` with `waitMs` park on a child with `until = now + timeoutMs` and no
selection. Delegation signals the effect when its named agents
satisfy its mode or user input arrives with `delivery: "steer"` on the blocked head. Abort wakes it
with the abort flag. Every wake settles with a report for each ended request and a phase for the
rest. The parent may wait again. The intent arguments name the agents; child sessions and parent
delegation records hold their answer state.

Richer rendering than a `Selection` comes from the commit's typed `ToolClass`, never a larger core
widget shape.

### Retries

A retryable provider failure produces a complete assistant error message and a `retry` outcome.
The step commits that assistant message with `outcome: { kind: "failed", failure }`, increments
`attempts`, and writes the run phase as `retry { at, retries, failure }`. `retries` counts
consecutive retryable failures and resets after a successful response. Before `at`, a step returns
the durable deadline. At or after `at`, it calls `respond` again. `drive` waits in process. A
step-at-a-time host schedules another entry.

Failure class determines retryability and any provider-requested minimum delay; retry policy adds
backoff.

### Checkpoints

A `checkpoint` commit is a context boundary. It stores a portable summary, retained tail,
`tokensBefore`, optional usage, and optional provider checkpoint material. The context projection
starts at the newest checkpoint. It uses provider material only when provider, API, and model all
match. Transcript and usage projections keep the checkpoint as history.

Threshold and overflow produce `Turn` checkpoint outcomes. Under the head lease, `runs.compact`
writes a manual checkpoint through `writeCheckpoint` with the branch's declared model and thinking
level. The checkpoint emits an ordinary `commit` event. `refs/compactions/<head>` records in-flight
work. A `compaction` event and snapshot field carry that record so watchers can show progress and a
later step can settle abandoned work.

### Two ways to run

- **Hot loop.** A desktop, TUI, or VM calls `drive`, renews one lease, and executes until idle,
  waiting, finished, busy, or fenced.
- **Step at a time.** A request, queue consumer, or alarm calls `step`, persists nothing locally,
  and schedules another entry when the outcome requires one.

Both have the same durable behavior. A runner **must not** require in-memory state beyond a step.
The hot loop only keeps the lease warm.

## Admission is open

`submit` always creates a pending `Change`, never appends to the head, and never inspects or
acquires the runner lease. It stamps `delivery` as `steer` or `next` and `kind` as `user`,
`answer`, `passive`, or `report`. Later code never infers them from the body.

Submission reads the selected tip, writes a change whose `previous` names it, then compares and
moves the tip ref. Tip conflicts retry internally. With a caller key, the same CAS writes
`refs/keys/<key>`. A competing key returns `duplicate` with the first change oid.

### The inbox

Each head has independent `steer` and `next` chains. `steer` lands at response boundaries and while
idle. `next` lands only while idle and after `steer`, so steering may overtake older next-run input
without rewriting either chain.

For each delivery, `tip` names the newest change and `base` names the last landed change. Pending
is the half-open interval `(base, tip]`, walked through `Change.previous` and presented oldest
first. The store holds no pending array. Concurrent submissions form one chain because every tip
move compares its predecessor.

`drain: "one"` lands through the first user change, including passive changes ahead of it.
`drain: "all"` lands the whole selected delivery. While a live run still owes an answer, the
boundary drain takes only leading answer and report changes.

Admission is one pure decision over the head and the selected batch's lead:

| Head \ Lead | `none` | `user`                           | `passive`                                              | `report` | `answer`                                                                       |
| ----------- | ------ | -------------------------------- | ------------------------------------------------------ | -------- | ------------------------------------------------------------------------------ |
| `idle`      | `wait` | `start` a user run and new chain | `settle` under the terminal run; `wait` if none exists | `wait`   | `start` a continuation and inherit its chain when authorized; otherwise `wait` |
| `live`      | `wait` | `join`                           | `join`                                                 | `join`   | `join`                                                                         |
| `settling`  | `wait` | `wait`                           | `wait`                                                 | `wait`   | `wait`                                                                         |

For every non-empty live cell, an agent change returns `handoff` instead of `join`. The run ends
and the batch remains pending. `step`, `runs.wait`, and relocation use this decision. Only building
an answer lead reads its authorization record. Landing derives the next run and ref updates from
the decision.

`pending` walks both chains, drops tombstoned changes, and sorts visible items by submission time
and oid. All clients read that store projection and see the same list.

### Cancel and redeliver

Cancel does not rewrite a change or splice a chain. It writes a blob behind
`refs/cancelled/<change>` and asserts the source inbox base in the same CAS. Landing asserts that
every selected change has no tombstone. A cancel racing landing
therefore settles as `cancelled` or `landed`, never both.

Redelivery edits a pending item in one atomic update. It may change `delivery`, move the item with
`before`, replace a pending user message's content, or combine those changes. It tombstones every
change from the splice point onward, asserts the source base, and rewrites that suffix onto the
target chain. A rewritten copy keeps its body, kind, author, and submission time, records
`supersedes`, and gets a new oid. An unchanged prefix keeps its ids. No intermediate state shows an
item in both deliveries or in neither.

### A submitted message is never lost

Only landing or an explicit cancellation tombstone hides a pending change. Failed, aborted, and
superseded runs leave changes pending.

Run cancellation is one-way. The runner cancels the in-flight call, preserves its output, settles
admitted tool work, and ends as `aborted`. A queued user message starts a new run without clearing
the stopped run's flag.

User input starts model work. An answer to a request authorized by an unstopped run also starts
it. The idle landing CAS consumes that authorization once beside the head, inbox base, and new run
refs. Stop and requester failure rewrite outstanding authorizations to `input`. Command
completions, participant child requests, and answers with revoked or consumed authorization remain
queued until user input. Configuration may land without starting model work. To `runs.wait`, a
head with only deferred unauthorized completions is `idle`. Compaction may continue an authorized
run but cannot revive a cancelled one.

Core does not repair a submit whose outcome is unknown. The client retries through an outbox that
closes the gap between Enter and a durable receipt:

1. Mint a key on Enter, keep the message locally as `sending`, and render it immediately.
2. Submit with that key. On a network failure, keep the row and retry with backoff using the same
   key until it succeeds or the user cancels the local send.
3. Treat `queued` and `duplicate` as durable. Match the local row by identity, never content. The
   receipt names the change, and the key appears on the change, pending item, and landing commit.
   Receipt and watch may arrive in either order. A message already shown by the watch draws nothing
   from its late receipt.

The key is correlation for the sender, not authorization, and stays outside the message the model
reads.

### Who runs?

A host that called `attach` watches session events, wakes a head driver when head, queue, run, or
effect refs move, and races for the head lease. One runner wins. Thin clients do not call
`attach`; their submissions remain durable until a host volunteers.

Attribution is optional `Actor` data with `clientId`, `userId`, and `device`. A host sets it once
in `NyteOptions`, and the SDK writes it on participant objects and ref events. Attribution is not
authorization.

## Many runners, one store

Heads and sessions are independent. Runners may lease different heads in one session, and any
number of sessions may share a backend. A participant may request abort without the lease; the
runner honors the new run ref at its next publish.

The `Store` contract has four namespaces on every `Session`:

| Namespace | Required behavior                                                                                                        |
| --------- | ------------------------------------------------------------------------------------------------------------------------ |
| `objects` | Idempotent content-addressed put, get, list with write time, ancestry `chain` and `commits` reads, and collector delete. |
| `refs`    | Read, prefix list, and atomic multi-ref CAS with assertions, optional lease, actor, reason, and events.                  |
| `leases`  | Acquire, renew, release, and read fenced execution rights.                                                               |
| `events`  | Fenced append, cursor read, last, floor, trim, and gap-free ordered watch.                                               |

A `refs.update` transaction checks the lease and every `from`, applies non-assertion writes,
allocates sequences, appends ref and supplied events, then publishes to watchers. A backend that
cannot do this atomically **must not** host the kernel.

Two backends ship. The SQLite backend uses five tables:

| Table      | Holds                                                            |
| ---------- | ---------------------------------------------------------------- |
| `sessions` | Session id, creation time, next event sequence, and event floor. |
| `objects`  | Session, oid, object kind, body, and write time.                 |
| `refs`     | Session and ref name to oid.                                     |
| `leases`   | Session and lease name to owner, fence, and expiry.              |
| `events`   | Session and sequence to time and event body.                     |

SQLite serializes writes with `BEGIN IMMEDIATE`. One session row allocates every event sequence.
Trimming deletes event rows and raises the session floor in one transaction.

The Postgres backend, exported as `@nyte-ai/core/postgres`, uses the same five tables under a
`nyte_` prefix plus a `nyte_schema` version row. It uses row locks instead of `BEGIN IMMEDIATE` and
supports server and serverless placements over a network.

## Deployment

Three placements use the same store and step contract:

- **Embedded.** The host process is also runner and client. The TUI and desktop use a local store
  and in-process watch.
- **Server.** A long-lived host owns a store, attaches runners, and exposes SDK operations over a wire.
- **Serverless.** A request or alarm opens a session, calls `step`, and exits. A remote backend
  supplies the same four authorities.

Only embedded clients ship today. `@nyte-ai/server` supplies a tested request handler, not a
listener or hosted service. An MCP stdio server is a child of the plugin host process, so it exists
in embedded and server placements; stateless placement remains open.

The implemented wire follows the SDK's operation table in `@nyte-ai/protocol`:

```text
GET  /v1/info                          host release and wire version
POST /v1/call/{operation}              validated SDK input and discriminated reply
GET  /v1/watch?sessionId=id&after=seq  projected session events over SSE
GET  /v1/watch?sessionId=id&live=1     the same stream, starting at the tip
```

The server **must not** attach a runner or step for a connection. Host composition opens the
store, provides trusted plugins and models, and decides when runners attach. Disconnect or server
close **must not** cancel accepted submissions or stop host runners. Close rejects new work and
ends streams; dispatched SDK operations may finish.

Authentication precedes body parsing. Optional permissions decide each operation from validated
input and each watch from its validated session id before SDK access. A supplied policy **must**
deny unlisted operations and watches. Authenticated version discovery remains available. The
server does not filter result pages. A host **must not** grant a directory operation such as
`sessions.list` to a session-scoped caller unless it may see every returned item. Hosts own device
pairing, credential storage and revocation, encryption, and relays. Permissions do not revoke
admitted streams; immediate revocation requires terminating affected connections.

Store sequences and SDK cursors are not interchangeable. Several SDK events may share one durable
sequence, and host activation notices are not ordered by it. After any wire disconnect, the client
**must** take a fresh snapshot, watch from its `seq`, and fold replayed objects by identity. The
last SSE `id` may skip other projections of that sequence, even above the floor. A protocol
**must** preserve SDK plain objects and discriminated outcomes for non-TypeScript clients.

## Events and views

A reconnect within the retention window replays missed deltas. Below the floor, `CursorExpired`
makes the client drop incremental state, take `sessions.snapshot`, and resume after its `seq`.

The collector marks current ref targets and both ends of retained ref events, follows object links
including commit `change` provenance, and sweeps only unmarked objects older than the supplied
grace period. To reclaim history, a host calls
`trimStream` to advance the floor and drop old ref-event roots, then `collect`.

The kernel supplies floor, trim, mark, grace, and sweep, but no default event window, grace period,
or schedule.

| Projection area | Exports                                                                                      |
| --------------- | -------------------------------------------------------------------------------------------- |
| changes         | `appendTurnChanges`, `changesFromTurns`, and `EMPTY_CHANGES`                                 |
| context         | `projectContextStatus`                                                                       |
| directory       | `sessionDirectoryEntry`                                                                      |
| live parts      | `foldLiveParts`, `livePartKey`, and `EMPTY_LIVE_PARTS`                                       |
| patch           | `parsePatchFacts`, for a client that draws hunks; counts come stamped on the commit          |
| transcript      | `appendTranscriptCommit`, `transcriptFromCommits`, `turnPartId`, and `EMPTY_TRANSCRIPT`      |
| tree            | `collectAbandoned`, `navigationTarget`, and `projectTree`                                    |
| usage           | `commitUsage`, `usageTokens`, `emptyUsageSummary`, `mergeUsageSummaries`, and `projectUsage` |

Projections in `@nyte-ai/client` **must not** write or classify. Tool parts carry their commit's
`ToolClass`, and turns carry their assistant commit's `Failure`. An unknown tool is `custom` under
its label, so every settled message renders without a plugin.

## Plugins

Plugins are host composition. They may contribute tools, commands, prompt sections, resources,
settings, agents, and hooks. The host resolves them only after workspace trust and passes the list
to core.

Hooks intercept a run and return typed results. They are `transform_context`,
`transform_transcript`, `before_request`, `before_tool`, `after_tool`, `before_compaction`, and
`cache_warming_decision`. `transform_context` sees the conversation without system messages and may
replace it or that request's system prompt. `transform_transcript` sees the full transcript
including system messages, and core sends its result as returned. Both change one request, never
the branch. `before_tool` handles policy. Its handlers run in registration order, chain `modify`
decisions, and stop on the first `reject` or `error`. A throw becomes `error`, so policy fails
closed.

`api.events.subscribe` receives the same post-hoc `SessionEvent` stream a client folds. Listener
returns and throws never reach the run.

A command runs immediately with its typed argument and returns user text, a `prompt` for the
client's next user message, or nothing. `api.session` gives a plugin `info` with name and child
status, `rename`, and `context` with the main branch's next model view. Other needs require a new
operation here, not store access.

Plugins reach users outside the conversation through `diagnostics.notify`, the `status` registry,
and tool waits. `diagnostics.notify` carries a title, message, and sound choice. `status` holds
short items beside the model. A tool parks with `throw new ToolWait({ selection, until })` or
returns `{ kind: "wait", selection, until }` from its wake handler. These travel as `notification`
and `status_changed` events and waiting-effect data for every client to render. No payload names a
plugin, and `api` has no `ui` namespace for calling an attached client. A tool may declare
`availability: "foreground"` when it cannot run after its session enters the background. This host
placement metadata does not determine its name or selection.

Activation is per session and host process. Setup stages and validates contributions before
publication. It may read session facts but cannot rename the session or write storage. A failed
candidate leaves the active set unchanged. Disposed registrations and callbacks cannot mutate it.

Plugin replacement waits for the offered response and tool batch, including parked calls and wake
handlers, plus active commands and callbacks. It returns `queued` instead of blocking its caller.
Other sessions continue. `api.defer` schedules resource changes at that boundary; MCP uses it
before releasing connections. `plugins_changed` reports publication, not preparation.

Handlers **must** be re-entrant. Cross-step state belongs behind session fact refs or in a
host-owned service, never in a runner closure. Plugin failure **must not** weaken a policy
decision into permission.

Facts are blobs behind `refs/facts/<key>`. The SDK stores `name`, `parent`, `pinned`, `archived`,
and `cwd` there. Plugin storage uses per-plugin prefixes. A plugin sees its own setting change as
a `fact` event with its key and new value.

The process owns MCP connections; each session selects which to use. A pool shares one connection
per server configuration across sessions. The plugin maps per-session on/off
settings to pool acquisition and release, then offers connected tools. The host-owned pool survives
plugin reloads that leave its configuration unchanged. Settings are per-plugin facts defaulting to
the manifest's `disabled`, and the plugin reacts to its own `fact` events. MCP tools use `never`
replay. Runtime tool discovery makes the pool notify on each status change and the plugin rebuild
its registries. After trust, the plugin reads server commands from the project manifest.

## Agents

An agent is a host-resolved session preset, not another runner type. A run stores its preset name
in `config`. Delegation needs no preset; `create` or `task` may supply an exact `provider/model`.
Both tool schemas list enabled choices across authenticated providers and refresh them per request.
One host model availability policy governs picking and execution. No separate subagent model
category or allowlist exists.

Without a model, a call selects `openai-codex/gpt-6.1-sol` with `high` thinking, then
`anthropic/claude-opus-5-5` with `medium` thinking if unavailable. An explicit thinking level
overrides that default. Creation fails if neither model is available. An explicit model never
falls back, and provider request errors never switch models.

A child receives shared session tools except delegation tools and tools marked for a present
participant. `create.system` or the prompt supplies its role and constraints. Before the prompt,
its config records the resolved model and thinking level. Availability is checked at creation and
each model request, including after restarts or preference changes. Losing availability fails the
request and never replaces an admitted child's model.

A child is a session addressed by `SessionId`. Its `parent` fact stores parent session, run, call,
and depth. `sessions.create({ parent })` writes it, `sessions.list({ parent })` finds children, and
plugins read `session.info().child`. A child persists until its parent calls `stop`. It is not a job
and does not appear in `jobs.list`. A panel uses the child's `SessionInfo` fields `parent`, `name`,
and `main` head `run`.

Parent tools are `task`, `create`, `send`, `await`, `read`, and `stop`. `task` creates, sends, and
awaits in one call. `send` enqueues a parent-authored user message on child head `main` with
`delivery: "next"` when idle or `delivery: "steer"` when live.

Before publishing the child change, the parent writes a request with owning run, call, head,
delivery state, and continuation state. The same CAS asserts the exact parent run object read by
`send`. If Stop wins, `send` abandons the request and publishes no child change. Model `send` and
`task` authorize one continuation under the parent's root. A participant message records `input`
instead.

When the child run that landed a request ends, one `completion` lands on the parent head. Its
`JobReport.delegate` carries the child, title, request identity, how the run ended, and last
assistant commit as the report. Request identity is the `commit` when landed or `change` when
stopped first. The request records the terminal child run oid, so delivery does not depend on the
trimmable event stream. Garbage collection retains that run object while the record is reachable.
Delivery submits under a stable key before marking the record delivered, so recovery cannot
duplicate a completion after a crash between writes. Each request gets one completion. A second
`send` gets another. Durable child completion **must** use stored state, never a process-local
registry queried by the model. Delegation tools exist only in root sessions, so depth is 1.

`await` waits on any or all named agents as [Wait and wake](#wait-and-wake) describes, and each
report also arrives as a completion. `read` returns child phase and latest turns without parking.
`stop` uses durable client cancellation for the child and its work, after which the child answers
no messages. Only children
created by the calling session are addressable; unknown ids return a tool error. Stopping a child
does not abort the parent run. Aborting the parent cancels its parked waits and revokes its
continuation authorizations. Children continue, but their later reports wait for user input.

## The SDK

The SDK uses plain data and one options object per operation. `SessionId` is its only branded id;
run ids, heads, oids, and sequences are plain named fields.

The root contract is:

```text
Nyte
  sessions   create · get · snapshot · metadata · list · rename · setPinned · setArchived · delete · configure
  messages   send · cancel · redeliver · list · pending
  runs       current · abort · wait · reply · compact · context · diff
  jobs       list · start · background · cancel
  heads      list · create · move · delete · merge
  workspace  list · current · select · forget · files
             vcs.snapshot · vcs.diff · vcs.contents · vcs.log · vcs.refs · vcs.stage · vcs.discard · vcs.commit · vcs.createBranch · vcs.push
  provider   models.list · models.default
  plugins    catalog · list · commands.list · commands.run · settings.list · settings.apply · resources.list · status.list
  watch({ sessionId, afterSeq? } | { sessionId, live: true })
  attach({ sessions? })
  advance({ sessionId, head?, signal? })          host-only, one leased kernel step
  sessionCwd({ sessionId })                       host-only location read
  relocate({ sessionId, workspace, plugins })     re-point one idle session
  reactivate()
  setPlugins(plugins, { sessionId }?)             applied | queued | rejected { error }
  close()
```

`NyteOptions` always supplies `store`, `streamFn`, `models`, and fallback `model`. Optional fields
are `actor`, `thinkingLevel`, `compaction`, stream options, `telemetry`, `onDiagnostic`, a workspace
backend, and `drain`, which is `one` by default or `all`. The backend provides a registry, `@`
file discovery, and `vcs` for every `workspace.vcs` operation at the directory resolved per call.
`@nyte-ai/host` supplies git. Static composition supplies `plugins` and `env`. Lazy composition
supplies `resolveActivation` and must not also supply static plugins or env.

`SessionInfo.activation` is host-local state. `activation_changed` is replayed once on every watch
with the latest durable sequence, but it is not ordered by the snapshot's `seq` and does not enter
the durable event stream. `reactivate()` asks the host resolver again for blocked sessions.

`runs.wait` resolves `idle` only after the run is terminal, nothing is pending, and the runner
released its lease. The last publish and lease release are separate writes, and `idle` promises a
free head.

The outcome unions a client switches on are exactly:

```text
ConfigureOutcome   queued { change } | unknown_model | unknown_agent
SendReceipt        queued { change } | duplicate { change }
CancelOutcome      cancelled | landed | not_found
RedeliverOutcome   redelivered { change } | unchanged | landed | not_found
AbortOutcome       requested { runId } | not_running
WaitOutcome        idle | waiting { runId } | cancelled
ReplyOutcome       signalled | not_waiting | not_found
CompactOutcome     compacted { commit } | aborted | nothing_to_compact | busy { run } | failed { code, message }
CreateHeadOutcome  created { tip } | exists | unknown_parent
MoveOutcome        moved { from, restored?: { commit, content }, summary?: Oid } | busy { run } | moved_since { tip } | not_found | failed { code, message }
DeleteHeadOutcome  deleted | not_found | busy
MergeOutcome       merged { tip } | stale | empty | no_stack

WorkspaceSelectOutcome  the reply to workspace.select
CommandOutcome     ran { output? } | prompt { prompt } | not_found | failed { message }

```

`failed` in `CompactOutcome` and `MoveOutcome` carries a `code`, so clients distinguish internal
failure from `inactive`, `busy`, `conflict`, `fenced`, or a stopped summary without parsing prose.

`RunInfo` carries `runId`, `head`, `origin`, `root`, kernel `RunPhase`, `startedAt`, `attempts`,
folded `config`, optional `abortRequested`, optional `awaitingReply` for a participant wait, and
current lease owner and expiry if present. It is not a terminal-state union.

## Invariants

Numbers are never reused. A superseded number remains with its reason.

Storage and session:

1. **Superseded.** Entries and records no longer exist. All six object kinds are immutable and
   addressed by the hash of their body.
2. **Superseded.** `seq` orders events only. Objects, refs, and leases do not receive a shared log
   position.
3. **Superseded.** Heads and facts are not the only mutable state. Every domain register is a ref,
   including queues, runs, effects, stacks, keys, cancellation, and deletion.
4. **Superseded.** The object store serializes typed objects directly. `toJsonValue` remains a
   boundary for unknown effect and progress payloads, not every durable write.
5. **Superseded.** Admission no longer chooses placed or queued by reading a claim. Every submit
   appends a change to one of the two inbox chains without taking a lease.
6. Concurrent participant writes linearize through ref CAS. A head advances only from its expected
   oid, so concurrent writers do not create an implicit fork.
7. Submission is idempotent under a caller-supplied key written with the inbox tip in one CAS.

Leases and runs:

8. At most one live lease exists per head name. Every runner ref write and event append is fenced,
   and a fenced transaction changes nothing.
9. Any runner may acquire an expired head lease and resume the run named by refs. It recovers an
   effect from its stored state and replay policy and never executes a stored result again.
10. **Superseded.** Tools no longer provision a result entry id. An effect ref names immutable
    intent, waiting, expired, signal, and result objects, and result messages enter the branch at
    tool-batch publish.
11. **Superseded.** The kernel cannot promise eventual completion without a runner. A run remains
    durable in its current phase until some process advances it.
12. A runner requires no in-memory state that outlives a step. The next step reads the head, run,
    queue, effect, and deletion refs.
13. **Superseded.** Wake input is not ordinary message admission. A waiting run is woken by a
    signal, a durable expiry claim, or abort.

Turn and boundaries:

14. **Superseded.** The kernel `Turn` receives the session and lease so it can maintain durable
    effect refs and emit fenced events.
15. A `length`-stopped assistant message fails its whole tool batch.
16. Tool results remain schema content parts end to end. Providers encode them at request
    time.

Events and views:

17. **Superseded.** The event stream is not the object store. It is a retained stream of ref moves,
    deltas, progress, and notices, and replay below its floor is refused.
18. **Superseded.** Streaming overlays cannot reference a provisioned entry. They reference run id,
    attempt, and content index until the completed message has a commit oid.
19. Projections read objects, refs, and events and never write authoritative state.

Policy:

20. Ported files change only within recorded divergence classes. New behavior composes around the
    port unless the divergence is named.
21. Extension failures are contained, extension capabilities may degrade across hosts, and project
    extension code **must not** load before trust.
22. Core has no global mutable defaults. The stream function and model catalog are injected.
23. No public SDK operation encodes a wall-clock execution budget. Lease TTL is failover metadata;
    hosts own execution budgets.

Plugins:

24. Nothing reaches the model except through host composition and plugin contribution. Built-ins
    are replaceable plugin contributions.
25. Contribution tables are a function of the activation list and the host-owned services its
    plugins read. Replaying the same list over a fresh draft with the same service state yields
    the same tables, and a service that changes **must** notify so the registry rebuilds.
26. Plugin session storage uses fact refs under the plugin's prefix. A plugin **must not** read or
    write another plugin's keys.

Agents:

27. An agent is one plugin registry contribution. There is no separate subagent runner type, and
    its mode never grants a capability.
28. A parent **must not** set a child's tools or a weaker policy through model-supplied arguments.
    Those arguments may choose its exact model and thinking level and, through `create.system`,
    add its role and constraints.
29. **Superseded.** There is no `operation_started` record. The run object stores configuration
    folded from config commits when the run starts.
30. A model-facing background job settles through durable session state, never through a
    process-local registry the model queries.

Presentation:

31. A settled tool result is self-contained. The transcript's tool part is the commit's
    `ToolClass`, `custom` for an unknown tool, and does not depend on ephemeral progress.

Heads and pending input:

32. **Superseded.** Head moves are logged as ref events, but the reflog is retained only above the
    event floor and may be trimmed.
33. Parent, base, and staleness remain. Summary navigation carries an abandoned path forward with
    one summary commit at the new base and never replays generated text.
34. **Superseded.** Pending input is not a record kind. It is the visible portion of the inbox
    chains after tombstones are removed.

Kernel CAS, queues, retention, and streaming:

35. Every ref CAS checks all `from` values before any write. `to === from` is an assertion that
    emits no event. Runner publishes **must** assert `refs/deleted` absent.
36. Each delivery is one `Change.previous` chain bounded by base and tip refs. Submitting **must not**
    replace it with an array or a client-owned queue.
37. Cancellation is a tombstone ref. Landing and cancellation assert the state they race over, so
    a change is cancelled or landed, never both. Redelivery tombstones the original and appends
    its replacement in one CAS.
38. Retention marks current refs and retained ref-event endpoints, follows all object links, and
    sweeps only unmarked objects older than grace. Raising the event floor **must** make older
    cursors fail with `CursorExpired` and take a snapshot.
39. A streaming delta is keyed by `(runId, attempt, index)`. It **must not** claim a commit oid
    before the complete message has been hashed.
40. A client outbox **must** persist one key from Enter through receipt and retry that same key.
    `queued` and `duplicate` both prove that the submitted change is durable.
41. A commit has exactly one context parent. `imports` record provenance and **must not** enter the
    model context chain.
42. Objects **must** be put before a ref names them. A failed CAS may leave loose objects and
    **must not** expose a partial ref update.
43. Head names are open, while inbox delivery is the closed pair `steer` and `next`. Every runner
    uses that timing and receives only the `drain` choice; `main` remains the SDK's default head.
44. TypeBox is the one schema library. A TypeBox type is the JSON Schema providers and MCP
    exchange, so `Tool.parameters` crosses the wire without conversion, and hosts validate
    their own boundaries with the same library. Only Node-side code imports `typebox/compile`;
    a renderer under a no-eval CSP checks through `typebox/value`.
45. A client **must** be able to render and answer any parked call that carries a `Selection`
    from the snapshot alone, and **must not** present one without as a request for input. Core,
    projections, and clients decide which is which by the selection's presence, never by the
    tool's name. A selection is made durable JSON and checked before the ref is written, so no
    plugin can leave an effect ref no reader can parse. Every parked call carries the waiting
    effect oid as `waitId`; re-parking the same call changes it so clients reset generation-local
    state.
46. A waiting effect's optional `until` is the authority for timeout. At or after it, a runner
    **must** claim the exact waiting oid by moving it to `expired` before it wakes the tool with
    `expired: true`. A participant reply and that expiry claim race through the same ref CAS, so
    only one wins. A client may close its panel but **must not** manufacture a reply or settle the
    effect. Re-parking after expiry requires a new wait and, when it should expire again, a new
    deadline.

## Open questions

1. **Long tools on stateless placements.** A command that outlives a request needs a process that
   can finish it or an external service that later signals its effect. The wait mechanism and the
   Postgres backend exist. Which process finishes the command and what wakes the next step remain
   open host wiring.
2. **Joining heads.** `heads.merge` fast-forwards a current stacked child into its parent. A general
   join of two named heads stays deferred until a product needs one.
3. **Identity and authorization.** `Actor` is durable attribution. ACL-scoped callers are host and
   protocol territory.
4. **Host-scoped plugin storage.** Fact refs belong to one session. Preferences shared across
   sessions need a host-owned store when a concrete plugin needs one. The first candidate is the
   MCP server toggle, since turning a server off most likely means for this machine. Today the
   per-session fact, defaulting to the manifest's `disabled`, stands in.
5. **Retention defaults.** Each host needs a retention window and schedule before users can rely
   on a specific undo horizon.
