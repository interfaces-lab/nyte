---
title: Send messages
description: Start a chat, send to it, wait for answers, and edit or reorder messages without sending twice.
---

Use this page when your code talks to the agent: starting a chat, adding to it while it works, and
knowing when it's done. Every example takes a `Connection` or a `Session`. A `Host` from `sdk.open`
is a `Connection`, so the code is the same in process and over the network.

## Start a chat with its first message

```ts
const { session, receipt } = await connection.sessions.start({
  name: "Fix the flaky test",
  content: "Find out why the date test fails on CI",
});

const end = await receipt.settled();

if (end.kind === "failed") console.error(end.failure.message);
```

`start` creates the session and sends its first message in one step, so a session never exists
without a message. Until you call it, an unsent chat is a draft that only your client knows about.

`start` resolves once the session's `before_send` hooks have accepted the message. If a hook refuses
it, the session is removed and `start` throws.

Everything except `content` is optional:

| Input           | What it does                                                                       |
| --------------- | ---------------------------------------------------------------------------------- |
| `id`            | Names the chat, its first message and its receipt. Minted when absent              |
| `name`          | The title shown in session lists                                                   |
| `workspace`     | A `WorkspaceId` from `connection.workspaces`. Absent, the host's default           |
| `parent`        | Makes this a child of another session                                              |
| `configuration` | Model, thinking level, agent and settings for the chat                             |
| `prompt`        | Adds a layer to the system prompt, or replaces it                                  |
| `isolation`     | `"worktree"` runs the chat in a new git worktree, removed with the chat            |
| `contextFiles`  | `false` reads no `AGENTS.md`, `CLAUDE.md` or similar files for this chat, for good |

Pass `id` when a draft already has one, or when you retry after your own process restarted. The same
id with the same input returns the same start. Different input under a taken id throws
`SdkError("invalid")`.

`isolation: "worktree"` throws `SdkError("unavailable")` when the workspace isn't a git repository.

## Send to a chat

```ts
const receipt = await session.send("Then add a regression test", { delivery: "queue" });
```

`content` is a string, or an array of parts for attachments and file mentions. `delivery` decides
how the message meets a run that is already going:

| Delivery            | When the agent sees it                                                 |
| ------------------- | ---------------------------------------------------------------------- |
| `"steer"` (default) | Once the live run's current tool calls finish, so it can change course |
| `"queue"`           | After the current run ends, as the prompt for the next run             |
| `"attach"`          | With the next run's prompt. It never starts a run on its own           |

`steer` and `queue` both start a run when nothing is running. A `steer` becomes a `queue` when the
model can't take messages mid-run or the run is stopping. Reports from subagents and jobs, and late
answers to a part's request, arrive attached and continue an agent that finished its last run.

`send` resolves once the host has admitted the message. It throws `SdkError("invalid")` when a
`before_send` hook refuses the message.

## Wait for what you need

`send` returns a `SendReceipt`. The receipt says the host has the message, not that the agent
answered. Wait on it for the moment you care about, or skip waiting and
[watch the view](/docs/sdk/guides/render-a-session) instead.

| Method      | Resolves                                                        |
| ----------- | --------------------------------------------------------------- |
| `landed()`  | When the message joins the history, with its `commit` and `run` |
| `settled()` | When the run the message started ends                           |
| `status()`  | Right away: `pending`, `settled` with the outcome, or `missing` |
| `stop()`    | Withdraws the message if it's still waiting, or stops its run   |

`settled()` resolves with one of these:

| Outcome     | Meaning                                                               |
| ----------- | --------------------------------------------------------------------- |
| `completed` | The run finished. `usage` holds its tokens and cost                   |
| `stopped`   | Someone stopped the run                                               |
| `failed`    | The run failed. `failure.class` says why, `failure.message` says what |
| `withdrawn` | The message was stopped before it reached the history                 |

An [edit](#edit-a-message) can also settle with a reason it didn't apply, listed below.

Pass a signal to stop waiting. Aborting the wait doesn't stop the run:

```ts
const end = await receipt.settled({ signal: AbortSignal.timeout(60_000) });
```

## Retries are already handled

`send` gives the message an id before anything reaches the network, and the message shows in the
view at once as `unsent`. If the host can't be reached, the SDK resends under the same id until it
answers, and the host admits the message once. You don't need your own retry loop. Sends to one head
go out one at a time, in the order you made them.

Only connection failures are retried. Any other error, such as a hook refusing the message, rejects
`send` and removes the message from the view.

Unsent messages are kept in memory, so they survive a dropped connection but not a restart of your
process. To survive one, pass `journal` to `connect`: an object with `load`, `put` and `remove`
over storage you own. On the next `connect`, the SDK resends every entry `load` returns.

To keep the id yourself, pass it. The same id with the same content returns the first send's
receipt:

```ts
import { asId } from "@nyte-ai/schema";

await session.send("Then add a regression test", { id: asId<"receipt">(savedId) });
```

## Edit a message

Editing sends new content in place of an earlier message. The chat rewinds to just before that
message, and the new one takes its place. Editing is also the only way to change a chat's first
message.

```ts
const view = await session.view();
const first = view.messages.find((message) => message.kind === "user");

if (first !== undefined && view.revision !== null) {
  const edit = await session.send("Find out why the time zone test fails on CI", {
    replace: first.id,
    expect: view.revision,
  });

  const outcome = await edit.settled();

  if (outcome.kind === "stale") console.log("Someone else changed the chat. Read it again.");
}
```

`expect` makes the edit conditional on the history you saw, so a message that arrived in the
meantime isn't lost. When the view's `revision` is `null`, the chat has no history yet. Read the
view again before editing.

An edit stops a live run first. Pass `running: "refuse"` to leave the run alone instead.

When the edit can't apply, the receipt settles with the reason:

| Outcome          | Meaning                                                         |
| ---------------- | --------------------------------------------------------------- |
| `stale`          | The history moved since the `expect` revision                   |
| `busy`           | A run is live and you passed `running: "refuse"`                |
| `pending-input`  | Messages you sent are still waiting to join the history         |
| `missing-target` | The message to replace isn't in this head's history             |
| `summary-failed` | You asked for a summary of what the edit removed, and it failed |

The replaced messages stay in the session's history tree.
[Branch a conversation](/docs/sdk/guides/branch-a-conversation#keep-a-summary-of-what-you-left) shows how to leave a summary
of them behind.

## Change a queued message

A message that is still waiting in the queue can change without rewinding anything.

```ts
const queued = await session.send("Then add a regression test", { delivery: "queue" });

await session.revise(queued.message, "Then add a regression test for the time zone");
```

The message keeps its id and its place in the queue. The session's `before_send` hooks check the new
content as they check a send. Pass `{ delivery }` to change how it meets the run ahead of it.

`revise` answers one of three outcomes:

| Outcome   | Meaning                                                               |
| --------- | --------------------------------------------------------------------- |
| `revised` | The message changed                                                   |
| `sent`    | The message already started. Nothing changed, and its run keeps going |
| `missing` | The message was withdrawn, or isn't queued on this head               |

To change a message that already started, [edit](#edit-a-message) it.

To reorder the queue, send the message again with `replace` and a `position`. `{ kind: "last" }`
moves it to the end and `{ kind: "before", message }` puts it ahead of another queued message:

```ts
await session.send("Run the linter", { replace: queued.message, position: { kind: "last" } });
```

## Hold a queued message while it's edited

A queued message starts as soon as the run ahead of it ends, even if someone is halfway through
editing it. `hold` keeps it waiting until the edit is saved:

```ts
const outcome = await session.hold(queued.message);

if (outcome.kind === "held") {
  await using held = outcome;

  await held.save("Then add a regression test for the time zone");
}
```

While the message is held, no run starts with it, and the messages queued behind it wait too.
Steers sent meanwhile still reach a running turn.

`save` revises the message, releases the hold and answers like `revise`. `release` lets the message
go unchanged. `await using` releases when the block ends, so an editor that throws or returns early
doesn't leave the queue stuck.

`hold` answers `sent` when the message already started, and `missing` when it was withdrawn or isn't
queued on this head.

A hold can end without you. `held.lost` resolves when that happens:

| `lost` resolves | Why                                                        |
| --------------- | ---------------------------------------------------------- |
| `sent`          | The message started anyway                                 |
| `missing`       | The message was withdrawn, for example by `receipt.stop()` |
| `lapsed`        | The SDK couldn't renew the hold in time                    |

After `save` or `release`, `lost` never resolves.

A few rules to code to:

- A head holds one message at a time. Holding another message on the same head ends the first hold.
- Don't call `release` while a `save` is in flight. A release that reaches the host before the
  revise can let the message start with its old text.
- The SDK renews the hold every 5 seconds, and each renewal lasts 20 seconds. If the host can't be
  reached, `release` answers `lapsing` instead of `released`, and the hold ends within 20 seconds.
- `release` and `await using` never throw.

## Stop everything

```ts
const { stopped, withdrawn } = await session.stop();
```

`stop` ends every live run in the session, withdraws every queued message, and returns the ids of
both. To stop one run, use `session.run(id).stop()`. To stop the work one message started, use its
`receipt.stop()`.

## Change the model

```ts
const outcome = await session.configure({
  model: { provider: "openai-codex", id: "{{modelId}}" },
  thinking: "high",
});
```

`configure` takes only what you want to change. It returns `configured` with the new selection, or
`unknown-model`, `unknown-agent` or `invalid` when the change doesn't fit the catalog. It doesn't
throw for those.

The change applies from the next model request, including the next request of a run that is already
going. A new model without a `thinking` level gets that model's default level.

`thinking` is one of `off`, `minimal`, `low`, `medium`, `high`, `xhigh` and `max`. `agent` selects
an agent a plugin declared.

When a person changes the model from a client, the host also remembers it as the default for new
chats. A change made by a tool call or a plugin doesn't change the default.
[Pick a model and sign in](/docs/sdk/guides/models-and-sign-in) covers the catalog and the default.
