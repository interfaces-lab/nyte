---
title: Render a session
description: Read a session's view once or live, draw its messages, and page in older history.
---

The host folds a session's events into a `SessionView`: the messages in order, the turns they belong
to, what is running now, and the files that changed. Your client draws the view. It never replays
events or merges streamed text itself.

## Read it once, or follow its rows

```ts
const view = await session.view({ tail: 100 });
```

`view` returns one snapshot. To keep a chat on screen current, open the host's rows with `openHost`
from `@nyte-ai/sdk/client`. It holds one socket per host address, and each `head` store on it
follows one head's rows:

```ts
import { headView, openHost, streamText, withStreamedText } from "@nyte-ai/sdk/client";
import type { StreamedText } from "@nyte-ai/sdk/client";

const live = openHost(address, {
  credentials: { kind: "token", token },
  client: { kind: "other", name: "my-client", version: "1.0.0" },
});

const store = live.head(session.id, session.name, { tail: 100 });
let texts: StreamedText = new Map();

const show = () => {
  const snapshot = store.snapshot();

  if (snapshot !== null) draw(withStreamedText(headView(snapshot), texts));
};

const stopRows = store.subscribe(show);

const stopText = live.text((update) => {
  texts = streamText(texts, update);
  show();
});
```

`subscribe` and `snapshot` make the store the shape React's `useSyncExternalStore`, Svelte, Vue and
Solid read; [Build an agent app](/docs/build/composition#add-the-files) shows each. `snapshot()` is
`null` until the first read arrives. `headView` turns a snapshot into a view, the same shape
`session.view()` returns without `seq`, and returns the same view for the same snapshot. Text a part
is still streaming arrives on `live.text`; `streamText` keeps it and `withStreamedText` lays it over
the view.

A send still in the connection's journal is not a row yet. `session.view()` shows it as `unsent`;
over a store, `unsentSends(connection, session.id, session.name)` does the same: `lay(view, seq)`
adds it to the view, with `seq` from `store.freshness()` while the store is fresh, and `subscribe`
calls you when the journal changes.

When the socket drops, the store marks itself stale (`store.freshness()`) and resumes from the last
change it applied once the socket is back, so nothing is missed or repeated. Call `store.close()`
when the chat leaves the screen, and `live.release()` when you are done with the host. In a browser,
pass `socket: ticketSocket()`, since a page can't put headers on a WebSocket.

`live.directory({ parents: { kind: "roots" } })` is the same kind of store for a session list: its
snapshot holds the listed `ids` in order and each one's `SessionInfo` in `rows`.

`tail` limits how many recent messages the view carries. The view always includes the turns those
messages belong to.

## Draw the messages

A message is either something the user sent or a part the agent produced.

```ts
import { isPart, text, thinking, tool } from "@nyte-ai/plugin/client";
import type { Message } from "@nyte-ai/sdk";

function describe(message: Message): string | null {
  if (message.kind === "user") {
    const status = message.status.kind === "landed" ? "" : ` (${message.status.kind})`;
    return typeof message.content === "string"
      ? `You: ${message.content}${status}`
      : `You: …${status}`;
  }

  if (isPart(message, text)) return message.state.markdown;
  if (isPart(message, thinking)) return null;
  if (isPart(message, tool)) {
    return message.state.phase === "settled"
      ? `${message.state.name}: ${message.state.outcome.kind}`
      : `${message.state.name}: ${message.state.phase}`;
  }

  return `[${message.partKind}]`;
}
```

`isPart` checks the part's kind and validates its state against the definition, so
`message.state` is typed inside the branch. Parts from plugins you don't render still have a
`partKind`, a `state` and a `status`. Fall back to something plain rather than dropping them.

A user message moves through three statuses:

| Status    | Meaning                                                     |
| --------- | ----------------------------------------------------------- |
| `unsent`  | In your client's journal, not yet acknowledged by the host  |
| `pending` | Admitted by the host, waiting for a run to take it          |
| `landed`  | Part of history, with its `commit` and the `run` it started |

A message you just sent is in the view at once as `unsent`. There is no separate optimistic state
to keep.

The built-in parts are `text` for answers, `thinking` for reasoning, and `tool` for tool calls. A
tool part goes through `calling`, `running` and `settled`; once settled, `outcome.kind` is `ok`,
`failed`, `interrupted`, `rejected` or `stopped`.

## Draw the queue

`view.queue` holds the messages waiting for a later run, oldest first. They are never in
`messages`, so draw `messages` as the transcript and `queue` beside the composer, without working
out which list a message belongs in.

A `steer` sent while a run works stays in `messages` as `pending` until the run takes it at its
next step. One the run can't take, because its model takes no messages mid-turn, the run is
stopping or the send changes the configuration, waits in `queue` instead. A `queue` sent while a
run works waits in `queue` and stays there after that run ends, until the next run takes it. An
`attach` waits in `queue` for the next run. A `steer` or `queue` sent to an idle head opens the next
turn, so it shows in `messages` at once. Reports from child sessions and jobs are never queued.

A send that is still `unsent` waits in `queue` while it retries, or while a run is live and it isn't
a `steer`. Otherwise it shows in `messages`.

`view.reportsHeld` is `true` when the head is idle and its last run didn't complete, or it hasn't
run yet. A report from a child session or a job then waits for the next prompt instead of starting
a run, so you can tell the user why nothing is happening.

## Show what is running

`view.execution` says what the head is doing right now:

```ts
import type { SessionView } from "@nyte-ai/sdk";

function status(view: SessionView): string {
  const { execution } = view;

  switch (execution.kind) {
    case "idle":
      return execution.lastRun?.end.kind ?? "ready";
    case "live":
      return execution.stopping ? "stopping" : execution.phase;
    case "waiting":
      return `waiting on ${execution.on.kind}`;
    case "retrying":
      return `retrying: ${execution.reason}`;
  }
}
```

A live run is `responding` while the model streams and `executing` while tools run. A waiting run is
parked on a part, a run, a job or a timer. When a run failed, `lastRun.end.failure` carries a
`class` such as `rate_limit` or `auth` and a message to show.

## Load older messages

A view with a `tail` stops at its oldest message. `history` reads the page before it:

```ts
const oldest = view.messages[0];

if (oldest !== undefined) {
  const page = await session.history({ before: oldest.id, limit: 50 });
}
```

For a scrolling transcript, `pagedViews` does the bookkeeping. It takes a source of views and
`history`, and keeps the pages you loaded at the front of every view it yields:

```ts
import { pagedViews } from "@nyte-ai/sdk";

// `views` is an AsyncIterable of the head's views, such as the head store's views above.
const paged = pagedViews({ watch: () => views, history: (query) => session.history(query) });

for await (const view of paged) draw(view);

// When the reader scrolls to the top:
const loaded = await paged.earlier(50);
```

`earlier` resolves with how many messages it added, and `0` once the first message of the chat is
showing. Iterate a `pagedViews` once.

## Mark a chat read

Each entry in `SessionInfo.heads`, from `session.info()` or a directory row, has `unread`, which
stays `true` until the connection's principal has read up to that head's tip. Reading or following
a head never marks it read, so a preloaded preview or a background store leaves the chat unread.
Your client marks it while the chat is on screen in a window that has focus, with the tip of the
head it drew:

```ts
const tip = (await session.info()).heads.find((head) => head.name === session.name)?.tip;

if (tip?.kind === "commit" && document.hasFocus()) await session.see(tip.id);
```

Call `see` again each time you draw a newer tip. A commit at or before the one already marked
changes nothing, and the SDK skips a call for the commit it last sent for that head. The view's
`seenThrough` is the time of the commit the principal last saw, so a message whose `at` is after it
arrived unseen.

## The rest of the view

| Field           | What it holds                                                              |
| --------------- | -------------------------------------------------------------------------- |
| `revision`      | The head's current revision, for `expect` on edits and moves               |
| `messages`      | User messages and parts, oldest first                                      |
| `queue`         | Messages waiting for a later run, oldest first                             |
| `turns`         | One entry per turn, with its state, step count and a summary of tool calls |
| `parts`         | Every part with its placement, including modal ones outside the transcript |
| `usage`         | Tokens and cost summed over every completed run in the head's history      |
| `execution`     | Idle, live, waiting or retrying                                            |
| `reportsHeld`   | Whether reports from children and jobs wait for the next prompt            |
| `background`    | Child sessions, jobs and browser pages, with whether each is still working |
| `configuration` | The `selected` configuration and the `effective` one after defaults        |
| `context`       | Tokens in the model's context and the size of its window                   |
| `changes`       | Files the session changed in its workspace                                 |
| `catalog`       | The commands, settings, skills, agents and tools this session can use      |
