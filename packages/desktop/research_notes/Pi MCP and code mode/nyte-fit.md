# Nyte fit for MCP discovery and code-mode execution

## What does Nyte already own, and which contracts can be reused?

### Takeaway

Nyte already has process-owned MCP connections, session-owned tool catalogs, schema-bound executors, run-specific availability filtering, and durable tool effects. Code-mode should reuse those boundaries. It should not create a desktop-owned session executor or replace intentional child no-prompt behavior.

### Takeaway

Start with an MCP-only catalog query and a single-target execution tool. A truly generic wrapper needs a core-owned run-scoped catalog/invocation contract, because the plugin's raw registry does not apply child or agent filtering.

### Inferences

#### Proposed minimal outline

1. **Limit the first release to MCP.** Keep the existing pool, config, per-session on/off facts, refresh handling, signal forwarding, and conservative replay policy. Do not wrap browser, question, bash, or delegation tools in the first version. The useful MCP and web-search tools remain available to children.
2. **Separate eligible execution catalog from model exposure in core.** Keep real tools registered and schema-bound. Resolve eligibility using existing child availability plus agent-name filtering, then project the model-facing definitions to discovery/execution wrappers for the chosen MCP subset. Do not delete real definitions merely to shrink the prompt. That would destroy the current execution catalog and break preset-name filtering.
3. **Use one eligible view for discovery and invocation.** Discovery returns matching stable IDs, descriptions, input schemas, and server/tool identity from that view, with a bounded result count/size. Invocation accepts one target ID plus JSON-object arguments and resolves it again in the caller's eligible view before execution. Reject missing, disabled, disallowed, or stale targets. Never search a process-wide pool or a parent's activation for a child call. Explicitly exclude wrappers themselves from their target catalog.
4. **Keep dispatch in core.** The new contract should provide run-scoped lookup plus normal prepare/validation/hooks/invocation, not hand plugins raw execute functions. The smallest first-use path is a single-target adapter under the existing outer effect. Persist target identity and effective inner args in the intent, forward the same signal/update/run context, and settle the wrapper's provider-visible call ID once. Keep `replay: "never"` for MCP execution. Resolve target eligibility before side effects; preserve the target identity for hook/provenance handling rather than silently reporting only the wrapper name.
5. **Do not claim a plugin-only adapter has full parity.** A pure `mcpPlugin` implementation can search its `active` handles and make one MCP call under a conservative outer effect. This is a smaller prototype and cannot expose unrelated foreground tools. But it needs explicit binding of raw handle tools, a deliberate policy for preset allowlists, and an explicit choice about inner versus outer hooks. It is not a generic invocation API.
6. **Preserve programmatic results.** Continue returning Nyte content blocks for the model. Add an explicit JSON data field, likely in details, for MCP `structuredContent`, and retain output-schema metadata needed by discovery/validation. Use `ToolError` when a server reports a structured failure so images/details are not collapsed to error text. Do not treat `content[0].text` as universal JSON.
7. **Avoid unnecessary provider work initially.** Two stable tools can return schemas/data through ordinary tool results. Use `addedToolNames` only if the chosen design actually introduces directly callable tool definitions after discovery. That separate design needs durable selected-tool state, reactivation behavior, marker restoration on effect reuse, and compaction/provider fallback decisions.
8. **Register through the shared host.** Enable the MCP presentation mode in `packages/host/src/plugins.ts`, with configuration owned beside existing MCP settings. Desktop should not grow a parallel execution endpoint or new approval layer.

#### How to avoid foreground exposure through a wrapper

- Filtering only the wrapper is insufficient. An unrestricted wrapper can survive child filtering while calling a foreground-only inner tool from `api.tools.list()`.
- Core should resolve each inner target from the same post-availability, post-agent-policy catalog the normal executor uses. Discovery must use the same catalog, or it can advertise tools the execution path refuses.
- A wrapper being permitted by a preset must not implicitly permit every target. Existing presets name real tools; retain that interpretation or explicitly define new wrapper policy. Do not infer target permission from the model's knowledge of a tool name.
- This is enforcement of existing availability and agent choices. It does not add prompts to children, remove MCP/search, or require children to copy all parent settings.

### Gaps

- Product choice: Are the two tools MCP-only, all session tools, or a selected subset? MCP-only removes most wait and nested-job complexity.
- Are discovered tools returned as schemas for the execution wrapper, or dynamically exposed as direct provider tools? These are different integrations; provider deferred-loading support only helps the latter.
- Should wrappers be optional or replace direct MCP exposure? Keeping both by default would not deliver the intended prompt-size reduction.
- How should MCP setting defaults relate to parent session choices? Current independent choices are valid. Inheritance would be a requested behavior change, not a safety repair.
- Sanitization/truncation can collide, and registry set overwrites an existing ID. A wrapper catalog needs an unambiguous stable target ID, or explicit collision detection, especially across server refresh/reload. ## What does code execution over tools still require?

### Takeaway

Reuse Pi's first-party `@earendil-works/pi-codemode` package for execution rather than porting its worker/QuickJS implementation. Nyte's missing work is the run-scoped adapter, structured result contract, limits policy, packaging, and durable program/nested-call semantics. The standalone runtime does not supply Nyte's crash guarantees.

### Inferences

#### Reuse instead of porting

1. Depend on the published standalone `pi-codemode` package at a verified compatible pin. Use its sandbox, worker, WASM loader, declaration renderer, and source parser. Do not port the QuickJS host/prelude or copy the coding-agent extension wholesale.
2. Implement a thin Nyte adapter in `packages/plugin` around a core-supplied eligible catalog and invocation contract. Create the sandbox per outer call or otherwise snapshot the caller's eligible tools; each injected callback routes to Nyte's invocation adapter with the callback cancellation signal combined with run/lease cancellation. Do not populate it from unfiltered `api.tools.list()`.
3. Keep the existing MCP pool/client initially. `pi-codemode` has no MCP dependency, so runtime reuse does not require transport migration. Evaluate `pi-mcp` separately if reduced dependency weight, progress, resources, or OAuth support is desired. Reuse its client rather than porting its transport implementation, but keep Nyte pool/session settings and add explicit input/output validation if migrating.
4. Package a worker entry that statically imports `@earendil-works/pi-codemode/worker` and ensure QuickJS WASM is available in Electron distribution and the native/Bun build. Pass `workerUrl`/`wasm` overrides rather than assuming bundled `import.meta.url` still names package files. Runtime behavior stays outside Electron renderer/preload.
5. Convert `CodemodeResult.output` to Nyte content, preserve partial output on failure with `ToolError`, and keep returned JSON/call summaries in structured details. Decide explicitly whether MCP `isError` results resolve as inspectable data or reject; do not inherit that choice accidentally from Pi's extension. Initially disable persistent script store or commit successful writes through a deliberate durable result contract, not a post-result process-local mutation.

#### Requirements before general code-mode

- **Use the package's narrow runtime boundary.** Inject only the eligible tools and the discovery helpers needed by the feature. Do not expose credentials, raw clients, or Pi's optional `models.*` helpers just because its coding-agent adapter has them. A standalone declaration schema is not input validation.
- **Use the package's actual termination.** Pass run/lease cancellation to sandbox execution and retain explicit finite timeout and memory settings. The package already kills tight loops in its worker, so Nyte does not need a new VM. Its pending-call abort signals still depend on host tools honoring cancellation, and cannot undo external effects. This is an execution isolation requirement, not a generic permission redesign.
- **Budgets below the response ceiling.** Specify wall-clock and CPU/memory limits, code size, nested-call count, concurrency, aggregate input/output bytes, image count/bytes, and log retention. Existing response limits and per-image normalization do not bound a loop that issues thousands of tool calls in one invocation. Cap discovery and output without silently corrupting structured JSON.
- **A typed data contract.** Code-generated args start as unknown, cross a JSON/schema boundary, and pass target preparation plus validation. Preserve both programmatic data and Nyte text/image content, details/title/usage, error status, and streaming updates. Keep failures distinguishable from successful data. Validate bridge replies, not just code inputs.
- **A first-release crash policy.** A whole program with side effects should initially be `replay: "never"`. A crash between side effect and outer settlement must report an interrupted/unknown outcome, not rerun the program. This avoids blind repeats but loses partial completion unless recorded. It does not promise external exactly-once execution or undo.
- **Durable nested calls for resumability.** If resumption is required, introduce deterministic inner call IDs tied to outer run/call plus a persisted sequence, store each inner intent/outcome before acknowledging it to code, and reuse settled outcomes. Keep each target's replay policy. Recovery must detect changed target/args rather than reusing the same sequence number for different work. External deduplication still needs service-specific idempotency support.
- **Determinism or a persisted continuation.** Replaying JavaScript from the top is unsafe if time, randomness, network, mutable discovery results, iteration order, or branch decisions change which effect occupies an inner ID. Either constrain/log those inputs and replay deterministically, persist a resumable program representation, or refuse program replay. The current kernel does not choose among these models.
- **Explicit wait scope.** Do not let an inner `ToolWait` accidentally park the outer wrapper and later invoke the wrong wake handler with `{code}` or `{target,args}`. For a minimal MCP-only version, exclude wait-capable general tools. To support question/browser/bash/task later, persist inner target, args, call ID, reply generation, and continuation state; wake the inner call, then continue or settle the outer program. Jobs/delegation completion routing must recognize those nested identities.
- **Keep result/progress durability.** If code filters intermediate results out of model context, still store the necessary inner outcomes/provenance for recovery. Keep emitted images in result content, not merely JSON logs. Preserve final error content and partial progress after cancellation; do not stringify all results into one text blob.

#### Recommendation

Prefer direct reuse of `@earendil-works/pi-codemode`, not a runtime port. First establish the eligible catalog/single-target invocation contract and MCP data envelope; these support both two-tool execution and a thin sandbox adapter. Keep Nyte's MCP transport initially and the whole script `replay: "never"`. Add resumable nested execution only if required. No new child approvals and no removal of useful MCP/search are needed.

### Gaps

- Pi APIs above were briefly inspected locally at the coordinator's supplied SHA. Other researchers own the detailed Pi audit. Publication/version availability, security testing, and full package conformance were not verified here.
- Does the public standalone runtime need streaming output or hard aggregate output limits? Its API returns output at completion and the inspected host accumulates output/calls in arrays. A final truncation adapter cannot enforce a pre-allocation host-output cap. If that is mandatory, prefer a small upstream API addition over a copied runtime. [Host accumulation, lines 95-97 and 183-197](https://github.com/earendil-works/pi/blob/86dfceec402ad77e563bf4feab5f26c42d5f5db6/packages/codemode/src/runtime/host.ts#L95-L197)
- Worker/WASM packaging must be verified in Nyte's Electron and native builds. These notes do not claim the package is already bundled or installed.
- Must code survive host restart, or is an interrupted result acceptable? This is the largest scope decision.
- Must code call waiting tools or start jobs/agents? Supporting only non-waiting MCP tools is a materially smaller implementation.
- Must code preserve successful inner calls when a later call fails? If yes, specify how the user/model sees partial completion and how retries avoid duplicating side effects.
- Should scripts see full structured MCP output and non-text resources, or only the current Nyte text/image projection? The existing bridge discards information and needs an explicit extension for data-centric code-mode.
- The MCP SDK pagination/output-validator behavior and effect-reuse marker loss deserve focused regression coverage if the integration depends on them. Neither was changed or tested in this research.
