Architecture maps / where a package boundary is, and what crosses it

Nyte is a git object database with messages in place of files, wrapped in an SDK, exposed over an HTTP wire, and drawn by three clients. Seventeen packages, one truth store, and a view layer that gets recomputed more times than it is written.

The shape worth noticing: protocol declares the view types and core computes them, so the wire contract and the projection are owned by different packages on purpose. desktop depends on nine workspace packages including both host and server and client. It runs a local host, an in-process HTTP server, and a remote client all at once.

Everything in kernel/ is a helper over four things: objects, refs, leases, events. A feature that can be a ref is a ref. The rule that keeps the whole thing sane lives in one file, admission.ts: only a batch carrying a user message may start a run. Background results, reconnects and recovery can wake a runner but never start one.

A runner keeps nothing in memory across a step. The next step re-reads refs. That is why a crash, a takeover, or a serverless scheduler calling sdk.advance one step at a time all behave the same.

The honest version of your complaint. Core computes the transcript once (transcriptFromCommits), ships it as Turn[] inside a SessionSnapshot, and then core/client replays the identical fold rules incrementally so a restore and a live append land on the same items. That second pass is defensible. It is core's own code, it is pure, and its whole reason to exist is that a stream cannot re-fetch a snapshot per token.

The third pass is where it goes wrong. Turn[] arrives at the renderer and each of the three clients rebuilds a display model from it independently: desktop in transcript-rows.ts + transcript-presentation.ts + work-group-presentation.ts, the TUI in a 3,245-line transcript.ts, iOS in chat/messages.tsx. Three answers to "what rows does this conversation have", three places a grouping bug can live, three places to fix it.

The counter-evidence, so you judge it fairly. Tool presentation was already pulled back into core. projectToolView and presentTool ship from core/views and all three clients call them. So the boundary is not missing, it just stops one level too early. It covers a tool call and not a turn, a group, or a row.

Also worth flagging. desktop/live-fold.ts projectLive is the defensible one of the dashed nodes. Its own comment says "no folding rules" — it turns core's ordered overlay into Map lookups for React identity. It is an index, not a second fold. Do not lump it in with the others when you decide what to move.
