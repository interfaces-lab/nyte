Architecture maps / where a package boundary is, and what crosses it

Nyte is a git object database with messages in place of files, wrapped in an SDK, exposed over an HTTP wire, and drawn by three clients. Seventeen packages, one truth store, and a view layer that gets recomputed more times than it is written.

The shape worth noticing: protocol declares the view types and core computes them, so the wire contract and the projection are owned by different packages on purpose. desktop depends on nine workspace packages including both host and server and client. Everything in kernel/ is a helper over four things: objects, refs, leases, events. A feature that can be a ref is a ref. The rule that keeps the whole thing sane lives in one file, admission.ts: only a batch carrying a user message may start a run. Background results, reconnects and recovery can wake a runner but never start one.

A runner keeps nothing in memory across a step. The next step re-reads refs. That is why a crash, a takeover, or a serverless scheduler calling sdk.advance one step at a time all behave the same.

The honest version of your complaint. Core computes the transcript once (transcriptFromCommits), ships it as Turn[] inside a SessionSnapshot, and then core/client replays the identical fold rules incrementally so a restore and a live append land on the same items. That second pass is defensible. It is core's own code, it is pure, and its whole reason to exist is that a stream cannot re-fetch a snapshot per token.

The third pass is where it goes wrong. Turn[] arrives at the renderer and each of the three clients rebuilds a display model from it independently: desktop in transcript-rows.ts + transcript-presentation.ts + work-group-presentation.ts, the TUI in a 3,245-line transcript.ts, iOS in chat/messages.tsx. Three answers to "what rows does this conversation have", three places a grouping bug can live, three places to fix it.

The counter-evidence, so you judge it fairly. Tool presentation was already pulled back into core. projectToolView and presentTool ship from core/views and all three clients call them. So the boundary is not missing, it just stops one level too early. It covers a tool call and not a turn, a group, or a row.

Also worth flagging. desktop/live-fold.ts projectLive is the defensible one of the dashed nodes. Its own comment says "no folding rules" — it turns core's ordered overlay into Map lookups for React identity. It is an index, not a second fold. Do not lump it in with the others when you decide what to move.

Pi is a layered monolith: a generic agent loop (pi-agent-core) and a provider client (pi-ai) sit underneath one thick host class, core/agent-session.ts, which owns queues, compaction, tools, extensions and persistence, and which every run mode (TUI, print, RPC) wraps with its own I/O. The persisted artifact is an append-only JSONL entry tree, and almost every view in the product is computed from that tree — often twice, once live from the event stream and once by re-walking the entries.

Dashed nodes recompute something the system already had. Five distinct double-derivations: (1) the transcript, rendered live from events and rebuilt from entries after resume, compaction, theme change, or thinking toggle; (2) cache-miss notices, computed once live and once again during rebuild by two functions in the same file; (3) usage and cost totals, walked out of getEntries by getSessionStats, by the footer on every frame, by getUsageCostBreakdown, and a fourth time by computeStats inside the exported HTML; (4) tool output, rendered by pi-tui components to the terminal and re-rendered by the same components at a fixed width 100 into ANSI, then converted to HTML for export; (5) the tree and branch path, walked by SessionManager in Node and walked again in JavaScript inside template.js. None of these share a memoized projection: the only cached view is AgentState.messages, which is itself a mirror of the entry tree.

The boundary is broad but one-directional in ownership: plugins never hold the Agent or a writable SessionManager. They get a ReadonlySessionManager, a read-only footer data provider, and mutation only through named actions. The strongest thing a plugin hands back is a veto or a rewrite: tool_call can block, tool_result can replace content, session_before_compact can cancel or return its own CompactionResult, and context can rewrite the message list on its way to the provider. Extension tool wrappers only adapt execution; interception moved into AgentSession's agent-core hooks so a reload swaps the runner without reinstalling anything.

OpenCode v2 is an event-sourced local agent server: a single Bun process owns a SQLite event log, folds durable session events into projected read models inside one Effect layer graph, and exposes the whole thing as an Effect HttpApi plus one SSE feed that every client — terminal, web, desktop — talks to identically. The interesting tension is that the authoritative fold lives in core, but each client re-runs a version of it locally to get streaming latency.

Two Effect service tiers do the structural work. makeGlobalNode nodes — Bus, Database, SessionProjector, SessionExecution — are process-wide and Session-ID addressed. makeLocationNode nodes — SessionRunner, tools, permissions, plugins, filesystem — are built per Location.Ref through a LayerMap and only acquired when a drain actually starts. Dashed nodes re-derive state that already exists upstream. The canonical owner is core: SessionMessageUpdater folds durable events into session_message rows inside the projection transaction, and GET /api/session/{id}/messages is the authoritative read. Nothing downstream is told to trust that fold exclusively, so the same fold is written again in client/solid/data.ts (for streaming latency) and a third time in tui/mini/stream-v2.transport.ts (for print mode, which never builds a store). Above that, TUI and app each own a private "which messages are visible" rule and a private transcript-grouping pass — the rules agree today by convention, not by construction.

The boundary is narrow by design: a Location plugin gets the Tools registration capability, never the registry, and each activation builds its tools in a plugin-owned Scope — closing it removes exactly that registration and reveals the next-latest one. Only tool execute.before has a failure channel; every other hook returns never on failure, so a plugin cannot fail a step by misbehaving in a hook. Sharing Tool.Tool does not imply equal authority: built-ins capture trusted Location services (FileSystem, PermissionV2) that application plugins cannot reach. codemode is not a plugin host — it is the sandbox that executes whatever ends up in the registered catalog.

All three systems fold events into a view. All three fold them more than once. What differs is how far down the shared code reaches before each client starts inventing its own answer.

What this says about Nyte

Nyte is the best of the three on this axis, and that is exactly why the remaining gap is worth closing. It already proved the pattern works: tool presentation moved into core/views and all three clients now call it instead of guessing. Nothing about that was hard. The same move has simply not been made for rows and groups.

The concrete next step is not a rewrite. It is one more view function beside projectToolView. Something like projectTranscriptRows(turns, options) returning the row list and work groups, with per-client rendering left where it is. That deletes most of transcript-rows.ts, most of work-group-presentation.ts, and a large part of the TUI's transcript class, and it gives iOS the grouping it currently does not have.

Leave desktop/live-fold.ts alone. It is an index for React identity, not a second fold, and moving it into core would make core care about a rendering framework.
