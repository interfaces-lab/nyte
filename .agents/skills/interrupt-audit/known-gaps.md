# Known gaps

These are real and not fixed. Each names what it would take. The commit that fixes one deletes its entry.

- **A `task` child can reach its parent twice.** A child that ends before its parent's `task` parks the wait has its report delivered and its answer returned by `task`, and a child stopped with its parent reports its stopped end. Holding a child's report until the call that started it settles would cover both.
- **A migration loads the whole store into memory.**
- **Pointer receipts written before the index stopped counting them stay in `pending_work`** until a migration rebuilds the index. They cost a sweep visit each, as before.
- **Search walks the session index when a name is rare.** `sessions.read` with `query` matches a lower-cased name column in activity order until `limit` match, about half a millisecond at 5,000 chats. Pinned chats read from their own index whatever the count. A trigram index would make search independent of the count.
- **A client newer than its host gets `invalid` for a filter the host does not know.** A phone at revision 25 against a Mac at 24 shows no search results and no older pinned chats until the Mac updates.
- **A client cannot tell which session a text frame belongs to.** Every open chat store takes every part streaming on the socket into its text map. A frame for a part its view doesn't hold notifies no one, but its entry stays until the store closes. A session on the frame would let the store drop it.
- **The next host cannot end every orphan of a killed one.** It ends a job's process group only when the group's leader still runs with its recorded start. A group whose leader exited while its children run, a job killed in the few milliseconds before its process was recorded, a job on Windows (no process groups) and a job on another machine keep the report that the command may still be running. Recording the session id beside the group on Linux and macOS would cover the first.
- **A tool that outlives its stopped run keeps its handles.** The run ends 3 s after the stop and refuses the tool's result, a nested tool call and a new command, but `invocation.session`, `sdk` and `env.exec` still send messages, call operations and start processes. Handles scoped to the call that refuse once it is abandoned would close it.
- **A Stop that another process on the store handles does not abort the run's tool.** The driving process sees the `stopping` event and marks the run fenced, but aborts its signal only at its next fenced write, so a command keeps running and the 3 s stop grace never starts. Aborting the run's signal on that event would cover it.
- **A run can wait out a 30 s lease after its host's jobs are reaped.** When the reaper deletes a lapsed holder's process ref before the run's claim does, `claimNow` finds the holder absent and waits for the lease to expire. Taking over at once from an absent holder, whose writes are all fenced, means extending the takeover-fence checks to absent holders.
- **A command over HTTP has no deadline.** A query or a receipt fails after 30 s unanswered, but the host runs some commands for as long as they take, so a Stop sent into a dead path stays unanswered. The app shows it stopping until the socket finds the link lost, 15 to 40 s later, and the person can press it again; Remove and Steer on a queued message show their busy state until their request fails.
- **A message removed after a post whose answer was lost can stay on the host.** The journal drops it without asking the host, so a post the host admitted before its answer was lost lands, and the chat shows it as the host's queued or landed row. A withdrawal that fails because the link drops at that moment is not retried. Keeping the removed entry journaled as a withdrawal, retried until the host answers, would cover both.
- **A send that expires while its window stays open puts its text back in the app's composer**, beside the unsent row that offers Send, because the composer treats the send's `timeout` like a refusal. Skipping the restore while the journal lists the receipt as expired would fix it.
- **An app query that failed on a lost link stays failed after the link returns.** Queries run with `retry: false` and no refetch on reconnect, and a query or receipt over a dead path now fails after 30 s, so file mentions and the model catalog show their error until their key changes. Refetching failed queries when health returns to `open` would fix it.
- **The app's sidebar never says its rows are stale.** With no chat open, nothing on screen shows that the link is down; only the composer says it is reconnecting.
- **A version mismatch is read from the socket's close reason.** The host closes with 1008 and a sentence, and the client matches its first words. A typed frame before the close needs a revision that both sides can rely on.
- **Mobile cannot answer an approval.** It shows that the run waits.
- **The TUI and mobile keep showing a chat that was deleted elsewhere.** Their head store now goes stale with `unknown`; neither acts on it, and neither reads `archived`.
- **A reconnect's reads wait for the welcome.** A resume sends `resume.held` only to a host whose welcome names revision 27 or later, since an older host refuses the field, so each chat's and list's read leaves one round trip after the hello instead of riding with it. Remembering the revision a host last named and reading again without `held` on `invalid` would remove the wait.
- **The HTTP stream channel wraps base64 in JSON in SSE.** A frame kind without the inner layers needs a revision bump.
- **A stalled git remote or formatter hangs its call.** `git push`, `blame` and the formatter run have no timeout.
- **A lease's holder notices a lapse up to one renewal late.** With presence the 20 s rule and the process fence cover it; changing it means running the takeover-fence checks.
