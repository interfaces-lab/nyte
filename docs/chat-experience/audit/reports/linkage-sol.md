# Subagents and foreground/background task linkage

## 1. How it works today

A subagent is a session carrying `parent`, originating `call`, and `workspace` (`packages/schema/src/sessions.ts:24–35`); `task` starts one and waits, whereas `create` returns immediately (`packages/plugin/src/subagents.ts:113–171`). SDK-backed app watches separately supply all sessions, direct children, session views, and workspace jobs (`packages/app/src/sdk.tsx:460–475`, `553–587`, `646–649`; job changes are folded in `packages/sdk/src/workspace.ts:215–241`). The chat directory joins session metadata and open views, propagating only the existence of active descendant runs (`packages/app/src/chats/directory.ts:65–106`, `140–159`). Transcript agent cards resolve a child by originating call; other delegate links resolve its session ID (`packages/app/src/conversation/subagent-call.tsx:266–293`, `375–390`). Clicking opens a child tray without desktop tabs, but a full preview chat with tabs (`packages/app/src/screens/session-conversation.tsx:373–390`); the agents tray lists active/failed direct children and a retained selection (`packages/app/src/conversation/tray/agents.tsx:50–83`). Shell tools start foreground jobs; releasing one clears `foreground` and settles the tool with a textual job ID (`packages/core/src/agent/tool-runner.ts:914–917`; `packages/core/src/builtins/environment.ts:296–327`). The terminals tray independently lists that chat’s running background jobs and is the sole production route into a job terminal (`packages/app/src/conversation/tray/terminals.tsx:49–65`, `95–112`; `packages/app/src/screens/session-conversation.tsx:502–512`). That terminal is a read-only output view, not a foreground reattachment; closing it detaches, while closing a user shell stops its process (`packages/app/src/workbench/terminal-runtime.ts:127–151`; `packages/app/src/workbench/terminal-store.ts:668–679`). Sidebar/tab marks use chat status, window exposure controls read marks, and notification plugins turn unseen root-run endings into text-only toasts (`packages/app/src/chrome/sidebar-rows.tsx:149–170`; `packages/app/src/tabs/use-window-tabs.tsx:136–175`; `packages/app/src/window/exposure.ts:33–69`; `packages/plugin/src/client/notifications.ts:18–29`; `packages/app/src/client-plugins.tsx:35–41`).

## 3. Proposed target shape

### One task identity; several views

Use a **derived task model**, not another persisted task engine:

- **Agent task:** stable child session identity, its direct parent/owner, originating call, workspace, and current execution. Keep run identity/result attached where known so an old result is not confused with a later run in the same child.
- **Process task:** `(workspaceId, jobId)`, with the SDK’s session owner when present. A user-created shell has a workspace owner, not an inferred owner based on whichever chat happens to be active.
- **Terminal:** a view of a process task, not a second execution. A pending terminal creation can have local view state until the SDK supplies its job identity.
- **Origin:** retain owner session plus originating call, and head/run where the source actually supplies them. Do not fabricate missing provenance. Use `SessionInfo.parent/call`, `JobView.session`, and `SessionView.background.startedBy` rather than comparing titles or commands.

Separate three axes:

1. **Execution:** starting, running, waiting for input, retrying, stopping, completed, stopped, failed, interrupted. Normalize `RunEnd` and `JobEnd` in one presentation adapter; preserve the underlying reason/code.
2. **Attachment:** foreground tool call or detached/background process. Opening an output panel changes neither. The current release operation is one-way; do not offer a fake “foreground” button that merely opens a terminal. A true reattach would need an explicit backend contract.
3. **Presentation:** inline row/report, tray list/detail, full chat, terminal panel, tab/sidebar badge, notification. Selection/expansion/closure changes presentation, not ownership or execution.

Each task exposes valid actions from its real execution: stop its own live run/process, open output/chat, reveal origin, return to owner. An aggregate “children still running” badge is not itself a stoppable run. If descendant stopping is offered, name it separately; `session.stop()` only stops that session’s runs/inbox (`packages/core/src/api/session.ts:585–612`).

The owned-work summary is computed once, keeping direct owner and ancestor roll-up distinct. Attention should remain visible even while other work runs; failures/unread results remain discoverable after activity stops. Keep bounded recent results, not an ever-growing tray. The existing `window/exposure.ts` remains authoritative for what the user is looking at.

## 4. First five changes

1. **Restore job access:** index the existing call/job link, make shell rows/reports open retained output, and expose recent ended jobs.
2. **Separate own run from owned work:** share job/child attention, failure, and live counts across trays, sidebar, and tabs.
3. **Add reliable return navigation:** child → parent/origin and job terminal → owner/origin, independent of tabs and workspace sharing.
4. **Correct Stop feedback:** read the returned end result; preserve feedback when the final live row disappears.
5. **Preserve meaningful task outcomes:** stop erasing failed awaits; give notifications typed destinations and owner-level result handling.

### Checks and limits

Reviewed source and counted production callers in the snapshot only. Ran read-only, in-memory Node checks against the real chat join, sidebar selectors, transcript projector, and presentation helpers using the repository’s existing fixtures: confirmed the waiting/failed-child parent states and invisible failed-await result described above. Also checked the distinction between tool success and textual shell exit codes. No test files, builds, dev servers, or snapshot edits were created. Electron/browser journeys, rendering, notification delivery, and live process cancellation were **not** executed; those conclusions are source-traced, not claimed as reproduced UI behavior.
